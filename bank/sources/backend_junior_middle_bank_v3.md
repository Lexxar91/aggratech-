## 2. Как читать карточки и считать автоматический балл

Кандидату доступны разделы «Кандидату», общие контракты и затем «Перенос». Ключи, скрытые данные и тестовые пакеты доступны разработчикам и проверяющим. Перенос — конкретная новая ситуация или изменение правила; результат первого этапа сохраняется. Если перенос меняет правило, основной код и изменённый код проверяются отдельно, а не одним противоречивым набором тестов.

**A — обычные случаи:** минимум два независимо запускаемых случая из карточки. **B — границы и ограничения:** каждый пункт обязателен. **C — перенос:** изменение из карточки. **D — сочетания условий и регрессии:** более сложные комбинации тех же объявленных требований. В D нельзя прятать новое требование.

| Балл задания | Проверяемое условие |
|---|---|
| 0 | Завершённая отправка не проходит ни одного случая A, включая синтаксически неработающее решение |
| 1 | Проходит часть, но не все случаи A |
| 2 | Все A проходят; хотя бы один B или C не проходит |
| 3 | Все A, B и C проходят; хотя бы один D не проходит |
| 4 | Все A, B, C и D проходят |

Это предложенная рубрика **результата выполнения**, а не шкала самостоятельности или полноты профессионального навыка. Доли тестов не усредняются: сто лёгких проверок не компенсируют провал обязательного ограничения. Каждый тест имеет ID и сопоставляется одному или нескольким явно указанным требованиям. Отдельно сохраняются флаги опасных нарушений: чужие данные, повторное списание, обработка неподписанного события. Балл задания сам по себе не разрешает подтверждать грейд при таком нарушении; решение об использовании этих флагов должно быть утверждено в политике оценивания до запуска.

Состояния `not_submitted`, `incomplete`, `environment_error`, `invalid_item`, `review_required` хранятся отдельно от числового балла. Незавершённый сеанс не превращается в 0 или в подтверждённый грейд. Исчерпание согласованного времени при отсутствии завершённой отправки — `incomplete`. Отказ инфраструктуры не считается ошибкой кандидата. Подозрение на внешнюю помощь — основание проверки, а не автоматически установленное списывание.

Автоматический раннер проверяет наблюдаемые результаты. Он не может по успешным тестам заключить, что кандидат сам нашёл причину дефекта. Для диагностики можно отдельно собрать контрпример и прогноз результата, проверяемые исполнением; устное объяснение оценивается на защите, отдельно от автоматического балла.

## 3. Общий технический контракт

- Целевая среда банка: Python 3.14, PostgreSQL 18. Конкретные patch-версии и образ среды фиксируются в манифесте запуска. Внешняя сеть в задачах не нужна.
- Python: сдаётся `solution.py`; импорт не выполняет ввод-вывод. Стандартная библиотека разрешена. Нельзя изменять входные записи, читать скрытые фикстуры, подменять адаптеры или пользоваться глобальным состоянием между вызовами.
- JSON-объекты в задачах не содержат повторных ключей и специальных чисел NaN/Infinity; неуказанные дополнительные поля допускаются и не меняют правила.
- Если не указано иное: ID, суммы, счётчики и версии — целые числа; суммы в минимальных денежных единицах, без float. Строки имён для сортировки — ASCII; все поля обязательны. NULL/None разрешён только там, где это явно сказано. Неверные типы вне условия не тестируются.
- SQL: сдаётся `solution.sql`. `:name` означает связанный параметр стенда, а не текстовую подстановку. SELECT-задачи не меняют таблицы. Имена и порядок результирующих столбцов указаны в ключе; альтернативный запрос принимается по результату, а не по совпадению текста. Таблицы каждой задачи изолированы.
- В таблицах идентификаторы строк уникальны, если явно не допускаются повторы. Все столбцы NOT NULL, кроме явно разрешённых. PostgreSQL bigint применяется к целым полям; тестовые суммы не переполняют bigint. Числовые итоги SUM сравниваются как точные числа.
- Fake-адаптеры записывают вызовы и побочные эффекты. Их методы имеют опубликованные ниже гарантии. У кандидата нет скрытой обязанности самостоятельно реализовать адаптер. Проверка использования гарантированной атомарной операции не доказывает умение построить саму эту операцию в промышленной БД.
- Раннер не оценивает скорость в миллисекундах как навык. Ограничения ресурсов защищают стенд и должны быть известны кандидату; зависание отдельно разбирается как дефект решения или стенда.

### Короткий словарь для карточек

- **Адаптер / стенд** — готовый объект или программа для работы с тестовым хранилищем, API и файлами. Его методы перечислены в условии; писать их заново не нужно.
- **Атомарно** — действие выполняется целиком или не выполняется; параллельный запрос не видит промежуточное состояние.
- **Идемпотентный повтор** — повтор запроса с тем же ключом не создаёт второй результат операции.
- **Outbox** — сохранённая вместе с операцией запись о сообщении, которое ещё нужно отправить.
- **Курсор** — значение, с которого API или запрос продолжает чтение следующей страницы.
- **Перенос** — второй этап: новый вход или изменённое правило, для которого нужно проверить или исправить своё решение.

В карточках не требуется угадывать универсальные HTTP-коды: нужные ответы определены условием.

### X1-PY-J — Суммы по командам

**Основной навык:** Python: словари, фильтрация, одноразовый итератор.

**Кандидату**

Напишите `totals(rows, paid_only=False) -> list[dict]`. Каждая запись: `{"team": str, "amount": int | None, "status": str}`. Верните `[{"team": ..., "total": ...}]` по алфавиту. None не прибавляйте; команду с подходящими строками только с None верните с 0. При paid_only=True учитывайте только status="paid". Команду без подходящих строк не возвращайте. Вход пустой → [].

**Перенос — показать после сохранения первого решения**

Теперь rows — одноразовый генератор. Он выдаёт те же записи. Получите тот же результат, не считывая генератор повторно и не сохраняя все входные записи в отдельный список. Проверка корректности — исполнимая; фактическую память дополнительно проверяют ресурсным стендом, а не одним тестом результата.

**Ключ для разработчика проверки**

```python
def totals(rows, paid_only=False):
    sums = {}
    for row in rows:
        if paid_only and row["status"] != "paid":
            continue
        sums.setdefault(row["team"], 0)
        if row["amount"] is not None:
            sums[row["team"]] += row["amount"]
    return [{"team": k, "total": sums[k]} for k in sorted(sums)]
```
Ошибка: сначала создать группы, а потом отфильтровать статус — останутся лишние команды.

**Обязательные пакеты автопроверки и рубрика**

- A: A:2+A:3 → A:5; B:4+A:1 → A:1,B:4.
- B: пусто; None → 0; cancelled при paid_only; отрицательная сумма; вход не изменён.
- C: те же результаты на одноразовом генераторе.
- D: смесь None, отрицательных сумм и статусов; перестановки входа.

Для этой карточки применяется шкала 0–4 из раздела 2; каждый перечисленный пункт — отдельный проверяемый признак.

### X1-SQL-J — Суммы в таблице

**Основной навык:** SQL: группировка и NULL.

**Кандидату**

Таблица `payments(team text, amount bigint NULL, status text)`. Верните `team,total` по team. Суммируйте amount; если подходящие строки есть, но все amount равны NULL, итог 0. При `:paid_only=TRUE` учитывайте только status='paid'. Параметр boolean, не NULL. Пустая таблица → 0 строк.

**Перенос — показать после сохранения первого решения**

Добавлены команда A только с cancelled и команда B с одной paid-строкой, amount=NULL. Запустите запрос с paid_only=TRUE: A отсутствует, B имеет total=0.

**Ключ для разработчика проверки**

```sql
SELECT team, COALESCE(SUM(amount), 0) AS total
FROM payments
WHERE NOT :paid_only OR status = 'paid'
GROUP BY team ORDER BY team;
```

- A: одна команда, суммы 2+3 → 5; две команды в алфавитном порядке.
- B: пусто; NULL; отрицательные суммы; оба значения paid_only.
- C: A только cancelled исчезает, B с paid/NULL остаётся с 0.
- D: смешанные статусы и несколько NULL; случайные перестановки вставок.

### X1-PY-M — Последняя версия перед подсчётом

**Основной навык:** Python: составной ключ и порядок преобразований.

**Кандидату**

Напишите `totals_latest(rows, paid_only=False) -> list[dict]`. Поля: team и status — строки; record_id, revision, revision_id — целые; amount — int или None. Для каждого record_id выберите максимальную пару (revision, revision_id); пары внутри record_id уникальны. Только затем примените фильтр paid_only и сложите суммы по командам. None означает отсутствие суммы; подходящая группа только с None получает 0. Возвращайте team,total по алфавиту. Вход может быть одноразовым итератором.

**Перенос — показать после сохранения первого решения**

Новая версия записи может изменить team и status. Старая версия была A/paid/10, новая B/cancelled/20. Без фильтра результат B:20; с paid_only=True результат [].

**Ключ для разработчика проверки**

```python
def totals_latest(rows, paid_only=False):
    latest = {}
    for row in rows:
        old = latest.get(row["record_id"])
        if old is None or (row["revision"], row["revision_id"]) > (old["revision"], old["revision_id"]):
            latest[row["record_id"]] = row
    sums = {}
    for row in latest.values():
        if paid_only and row["status"] != "paid":
            continue
        sums.setdefault(row["team"], 0)
        if row["amount"] is not None:
            sums[row["team"]] += row["amount"]
    return [{"team": k, "total": sums[k]} for k in sorted(sums)]
```
Ошибка: фильтровать paid до выбора версии — старая оплаченная запись может «вернуться».

**Обязательные пакеты автопроверки и рубрика**

- A: одна версия; две версии с разными revision, побеждает новая.
- B: tie по revision; None; пусто; фильтр после выбора; одноразовый ввод.
- C: новая версия переезжает из A в B и меняет статус на cancelled.
- D: комбинации переезда, ties, отрицательных сумм и перестановок.

Для этой карточки применяется шкала 0–4 из раздела 2; каждый перечисленный пункт — отдельный проверяемый признак.

### X1-SQL-M — Версии и агрегация

**Основной навык:** SQL: оконная функция и порядок фильтров.

**Кандидату**

Таблица `revisions(team text, record_id bigint, revision bigint, revision_id bigint, amount bigint NULL, status text)`. UNIQUE(record_id,revision,revision_id). Для каждой записи выберите максимальную пару (revision,revision_id), затем примените boolean `:paid_only`, затем суммируйте amount по team. Параметр :paid_only — boolean, не NULL: при TRUE учитывайте только status='paid'. Верните team,total по team. NULL не прибавляйте; подходящая группа только с NULL получает 0. Команду без подходящих выбранных версий не возвращайте; пустой результат — 0 строк.

**Перенос — показать после сохранения первого решения**

У записи последняя версия меняет team с A на B и status с paid на cancelled. В режиме paid_only запись полностью исключается; старую версию использовать нельзя.

**Ключ для разработчика проверки**

```sql
WITH ranked AS (
  SELECT r.*, ROW_NUMBER() OVER (
    PARTITION BY record_id ORDER BY revision DESC, revision_id DESC
  ) AS rn FROM revisions r
)
SELECT team, COALESCE(SUM(amount), 0) AS total
FROM ranked WHERE rn=1 AND (NOT :paid_only OR status='paid')
GROUP BY team ORDER BY team;
```
Эквивалентный DISTINCT ON допустим.

**Обязательные пакеты автопроверки и рубрика**

- A: одна версия; несколько версий и команд.
- B: tie; NULL; пусто; cancelled последняя после paid старой.
- C: изменение team/status в последней версии.
- D: старая версия имеет большую сумму; одинаковые revision с разными revision_id; перестановки вставок.

Для этой карточки применяется шкала 0–4 из раздела 2; каждый перечисленный пункт — отдельный проверяемый признак.

### X2-J — Проверка входящего события

**Основной навык:** HTTP и проверка подписи; Python.

**Кандидату**

Напишите `webhook(raw: bytes, signature: str, secret: bytes, content_type: str, enqueue) -> int`. HMAC-SHA256 подписывает исходные raw; signature — 64 строчные hex-цифры. Отсутствующая подпись представлена пустой строкой. Порядок: неверный формат или несовпадение подписи → 401; затем JSON: недопустимый UTF-8, невалидный JSON или значение не объект → 400; затем один вызов enqueue(parsed_dict) и 202. enqueue не падает. Сравнивайте подпись через hmac.compare_digest. На основном этапе content_type всегда application/json. Не отправляйте событие при отказе.

**Перенос — показать после сохранения первого решения**

Теперь допускаются разные content_type. После проверки подписи, но до разбора JSON отклоняйте всё, кроме точной строки application/json, с кодом 415. Это специально упрощённый контракт задачи, не общий HTTP-парсер.

**Ключ для разработчика проверки**

```python
import hashlib
import hmac
import json
import re

def webhook(raw, signature, secret, content_type, enqueue):
    expected = hmac.new(secret, raw, hashlib.sha256).hexdigest()
    if not re.fullmatch(r"[0-9a-f]{64}", signature) or not hmac.compare_digest(expected, signature):
        return 401
    # Строки проверки Content-Type включены в ответ после переноса.
    if content_type != "application/json":
        return 415
    try:
        value = json.loads(raw.decode("utf-8"))
    except (UnicodeError, ValueError):
        return 400
    if not isinstance(value, dict):
        return 400
    enqueue(value)
    return 202
```
JSON в фикстурах не содержит NaN/Infinity или повторных ключей объекта. Сравнение по времени не измеряется: instrumentation проверяет вызов compare_digest, независимое ревью проверяет его корректное применение.

**Обязательные пакеты автопроверки и рубрика**

- A: два разных корректно подписанных объекта → 202 и один enqueue.
- B: неверная подпись → 401; подписанный не-JSON/массив → 400; изменение пробела со старой подписью → 401; побочных эффектов нет.
- C: подпись → тип → JSON: bad signature+text/plain → 401, good signature+text/plain → 415.
- D: неверный UTF-8; пустая подпись; пустое тело с верной подписью; журнал compare_digest.

Для этой карточки применяется шкала 0–4 из раздела 2; каждый перечисленный пункт — отдельный проверяемый признак.

### X2-M — Приём события с повторной доставкой

**Основной навык:** HTTP, надёжность и подпись; Python.

**Кандидату**

Напишите `accept_event(raw, signature, secret, now, window, store) -> int`. raw — UTF-8 JSON-объект с event_id (непустая строка), timestamp (целое, не bool), data (объект). Подписаны исходные bytes, включая event_id и timestamp; signature — строка из 64 строчных hex-цифр HMAC-SHA256(secret,raw); отсутствующая подпись — пустая строка. Формат проверьте явно, совпадение — через hmac.compare_digest. Порядок отказов: подпись 401; JSON/схема 400; abs(now-timestamp)>window → 401; конфликт содержимого → 409; новый или идентичный повтор → 202. now/window — целые секунды, window>=0, граница включена. Для сравнения содержимого используйте точный raw, без нормализации.

Готовый store предоставляет единственную операцию `record(event_id, raw) -> "new" | "same" | "conflict"`. Она атомарно сохраняет событие и одну outbox-запись при new; same/conflict ничего не меняют. Хранилище переживает перезапуск. Очередь из обработчика не вызывайте. SQL писать не нужно.

**Перенос — показать после сохранения первого решения**

Первый процесс остановлен после record и до доставки сообщения. Запустите тот же запрос ещё раз с тем же store, затем готовый диспетчер. Событие должно остаться в outbox и примениться потребителем один раз. Срок окна в этом сценарии ещё не истёк.

**Ключ для разработчика проверки**

```python
import hashlib
import hmac
import json
import re

def accept_event(raw, signature, secret, now, window, store):
    expected = hmac.new(secret, raw, hashlib.sha256).hexdigest()
    if not re.fullmatch(r"[0-9a-f]{64}", signature) or not hmac.compare_digest(expected, signature):
        return 401
    try:
        event = json.loads(raw.decode("utf-8"))
    except (UnicodeError, ValueError):
        return 400
    if not isinstance(event, dict):
        return 400
    if not isinstance(event.get("event_id"), str) or not event["event_id"]:
        return 400
    if type(event.get("timestamp")) is not int or not isinstance(event.get("data"), dict):
        return 400
    if abs(now - event["timestamp"]) > window:
        return 401
    state = store.record(event["event_id"], raw)
    return 409 if state == "conflict" else 202
```

 Изменённый порядок ключей JSON считается другим raw и конфликтом — это открыто заданное правило, а не скрытая канонизация.

Outbox-диспетчер поставляется стендом: доставляет неотправленные записи с event_id, может повторить отправку; потребитель дедуплицирует event_id. Это проверка применения готовой атомарной операции, а не реализации outbox или доказательство exactly-once доставки.

**Обязательные пакеты автопроверки и рубрика**

- A: новое событие → 202; второе другое event_id → 202.
- B: bad signature; схема; timestamp=bool; now±window принимается, за границей отказ; same → 202; conflict → 409.
- C: остановка сразу после record, повтор и запуск диспетчера → одна outbox-запись, один применённый эффект.
- D: одновременно same/same и same/conflict через барьеры store; журнал запрещает публикацию до commit; изменённый timestamp со старой подписью отклонён.

Для этой карточки применяется шкала 0–4 из раздела 2; каждый перечисленный пункт — отдельный проверяемый признак.

### X4-J — Сбор страниц API

**Основной навык:** Python и HTTP: пагинация.

**Кандидату**

Результат: (items,calls), где calls — курсоры реально запрошенных страниц. fetch_page(cursor) возвращает {items:list[dict],has_more:bool,next_cursor:str|None}; в каждой записи есть целочисленный id. При повторе id сохраняйте первую запись целиком. Порядок — первое появление. При max_items<=0 верните ([],[]) без вызовов. Остановитесь на max_items уникальных элементов или has_more=False. Пустая страница не означает конец. В Junior цепочка конечна, без циклов; fetch_page не падает. Если has_more=True, next_cursor — строка.

**Перенос — показать после сохранения первого решения**

Последняя страница содержит повтор id с изменёнными полями и новый id. Сохраните первый вариант повторяющегося элемента и не запрашивайте next_cursor последней страницы.

**Ключ для разработчика проверки**

```python
def collect(fetch_page, start, max_items):
    items, calls, seen = [], [], set()
    if max_items <= 0:
        return items, calls
    cursor = start
    while True:
        calls.append(cursor)
        page = fetch_page(cursor)
        for item in page["items"]:
            if item["id"] not in seen:
                seen.add(item["id"])
                items.append(item)
                if len(items) == max_items:
                    return items, calls
        if not page["has_more"]:
            return items, calls
        cursor = page["next_cursor"]
```

**Обязательные пакеты автопроверки и рубрика**

- A: одна terminal-страница; две страницы с разными ID.
- B: max_items=0/-1 без вызовов; ровно лимит; пустая промежуточная страница; первая запись выигрывает.
- C: terminal-страница содержит старый и новый ID; следующий курсор не запрашивается.
- D: несколько пустых страниц; дубли внутри страницы; лимит достигается посреди страницы; calls совпадает с журналом.

Для этой карточки применяется шкала 0–4 из раздела 2; каждый перечисленный пункт — отдельный проверяемый признак.

### X4-M — Пагинация с циклом курсоров

**Основной навык:** Python: состояние и завершение.

**Кандидату**

Напишите `collect_safe(fetch_page, start, max_items) -> dict` с ключами items,calls,stop. fetch_page(cursor) возвращает {items:list[dict],has_more:bool,next_cursor:str|None}. Элементы содержат целочисленный id; первый элемент с данным id сохраняется целиком, порядок — первое появление. start — строка. При has_more=True next_cursor — строка. Пустая страница может иметь продолжение. fetch_page не падает. При max_items<=0 не вызывайте API; результат items=[] и calls=[]. calls содержит только реально запрошенные курсоры. stop: "limit" при max_items<=0 или достижении лимита; "end" при has_more=False; "cursor_cycle" перед повторным запросом уже запрошенного курсора. Приоритет: лимит элементов, затем terminal-страница, затем проверка следующего курсора. Возвращайте накопленные элементы. Цепочка либо конечная, либо повторяет курсор; бесконечная последовательность новых курсоров вне условия.

**Перенос — показать после сохранения первого решения**

Цикл a→b→a проходит через пустую страницу b. Затем измените max_items так, чтобы лимит достигался уже на a. В первом случае верните cursor_cycle, во втором limit без запроса b.

**Ключ для разработчика проверки**

```python
def collect_safe(fetch_page, start, max_items):
    items, calls, ids, cursors = [], [], set(), set()
    def result(stop):
        return {"items": items, "calls": calls, "stop": stop}
    if max_items <= 0:
        return result("limit")
    cursor = start
    while True:
        if cursor in cursors:
            return result("cursor_cycle")
        cursors.add(cursor)
        calls.append(cursor)
        page = fetch_page(cursor)
        for item in page["items"]:
            if item["id"] not in ids:
                ids.add(item["id"])
                items.append(item)
                if len(items) == max_items:
                    return result("limit")
        if not page["has_more"]:
            return result("end")
        cursor = page["next_cursor"]
```

**Обязательные пакеты автопроверки и рубрика**

- A: конечная цепочка; a→b→a вызывает только a,b и stop=cursor_cycle.
- B: цикл на себя; пусто; max_items<=0; разные множества для ID и курсоров.
- C: пустая b в цикле; при достижении лимита на a вернуть limit, не cycle.
- D: terminal с next_cursor=a возвращает end; terminal с достигнутым лимитом возвращает limit; пересечение ID при цикле.

Для этой карточки применяется шкала 0–4 из раздела 2; каждый перечисленный пункт — отдельный проверяемый признак.

### X6-M — Платёж и сбой внешнего сервиса

**Основной навык:** HTTP и надёжность; Python.

**Кандидату**

Напишите `submit_payment(account_id, key, amount, repo) -> dict` и `deliver_payment(operation_id, repo, provider) -> dict`. account_id — целое, key — непустая строка, amount — положительное целое в минимальных денежных единицах. Ответы: status и payment_id; новая/ожидающая операция → 202,None; завершённая → 201, сохранённый ID; тот же ключ с иной суммой → 409,None.

Готовый repo: `reserve(scope,amount)` атомарно создаёт сохранённую операцию и outbox-запись или возвращает существующую; результат — dict {conflict:bool,operation_id:str,state:"pending"|"done",payment_id:int|None}. `get(operation_id)` возвращает {amount,state,payment_id}; `complete(operation_id,payment_id)` атомарно сохраняет результат и помечает outbox выполненным, повтор с тем же ID безопасен. operation_id глобально уникален и сохраняется после перезапуска. provider.charge(operation_id,amount) возвращает int payment_id; повтор того же operation_id с той же суммой не списывает снова. Может поднять TimeoutError уже после списания. Не генерируйте новый operation_id при повторе. SQL и worker-планировщик предоставляет стенд.

**Перенос — показать после сохранения первого решения**

Провайдер списал деньги, но первый worker не сохранил ответ. Повторите deliver_payment с тем же operation_id после перезапуска. Получите прежний платёж и завершите локальную операцию.

**Ключ для разработчика проверки**

```python
def submit_payment(account_id, key, amount, repo):
    r = repo.reserve((account_id, "payments", key), amount)
    if r["conflict"]:
        return {"status": 409, "payment_id": None}
    return {"status": 201 if r["state"] == "done" else 202,
            "payment_id": r["payment_id"]}

def deliver_payment(operation_id, repo, provider):
    r = repo.get(operation_id)
    if r["state"] == "done":
        return {"status": 201, "payment_id": r["payment_id"]}
    try:
        payment_id = provider.charge(operation_id, r["amount"])
    except TimeoutError:
        return {"status": 202, "payment_id": None}
    repo.complete(operation_id, payment_id)
    return {"status": 201, "payment_id": payment_id}
```
Другие исключения, включая имитацию падения процесса, не глотать: стенд перезапускает обработчик. Без гарантии provider задача не обещает отсутствие повторного списания.

**Обязательные пакеты автопроверки и рубрика**

### Y3-M — Событие применяется один раз

**Основной навык:** SQL: транзакция, дедупликация и outbox.

**Кандидату**

Создайте PL/pgSQL-функцию `apply_event(p_account bigint,p_event text,p_delta bigint) RETURNS text`. Таблицы: counters(account_id bigint PRIMARY KEY,value bigint); applied(account_id bigint,event_id text,delta bigint,PRIMARY KEY(account_id,event_id)); outbox(account_id bigint,event_id text,delta bigint,PRIMARY KEY(account_id,event_id)). Счёт существует; event непустой; delta — целое любого знака. Внешних вызовов нет.

Новый (account,event): прибавить delta, записать applied и outbox, вернуть 'applied'. Повтор с той же delta → 'duplicate' без изменений. Повтор с другой delta → 'conflict' без изменений. Все изменения атомарны. Функция не делает COMMIT/ROLLBACK. Стенд вызывает её в транзакции SERIALIZABLE и при SQLSTATE 40001 полностью откатывает и повторяет транзакцию с теми же параметрами, не более пяти попыток. Исчерпание инфраструктурного повтора отдельно регистрируется; это не возвращаемый статус функции.

**Перенос — показать после сохранения первого решения**

Сначала стенд откатывает всю транзакцию после вызова функции. Затем повторяет событие и фиксирует транзакцию, но имитирует потерю подтверждения очереди. Следующая доставка должна вернуть duplicate и не менять счёт повторно.

**Ключ для разработчика проверки**

```sql
CREATE OR REPLACE FUNCTION apply_event(p_account bigint,p_event text,p_delta bigint)
RETURNS text LANGUAGE plpgsql AS $$
DECLARE inserted boolean; old_delta bigint;
BEGIN
  INSERT INTO applied(account_id,event_id,delta)
  VALUES(p_account,p_event,p_delta)
  ON CONFLICT (account_id,event_id) DO NOTHING
  RETURNING TRUE INTO inserted;
  IF inserted IS NOT TRUE THEN
    SELECT delta INTO old_delta FROM applied
    WHERE account_id=p_account AND event_id=p_event;
    IF old_delta = p_delta THEN RETURN 'duplicate'; END IF;
    RETURN 'conflict';
  END IF;
  UPDATE counters SET value=value+p_delta WHERE account_id=p_account;
  INSERT INTO outbox(account_id,event_id,delta) VALUES(p_account,p_event,p_delta);
  RETURN 'applied';
END;
$$;
```
Ошибку сериализации не перехватывать и не превращать в успех. Протокол повторов предоставляет стенд: сам по себе этот ответ не подтверждает умение написать retry-loop.

**Обязательные пакеты автопроверки и рубрика**

- A: новое событие увеличивает счёт и создаёт обе записи; другое событие того же счёта тоже применяется.
- B: duplicate/conflict не меняют состояние; одинаковый event у разных счетов независим; отрицательная delta.
- C: rollback после вызова → ни одного изменения; повтор после commit до ack → duplicate, без второго изменения.
- D: два соединения отправляют один event, полный retry после40001 → одно применение; разные события не теряются; outbox=одна запись на применённое событие.

Для этой карточки применяется шкала 0–4 из раздела 2; каждый перечисленный пункт — отдельный проверяемый признак.

```python
def retry(send, sleep, max_attempts, delay, retryable=frozenset({503})):
    attempts, status, waits = 0, None, []
    while attempts < max_attempts:
        status = send()
        attempts += 1

        sleep(delay)
```

- C: retryable={503,429}: [429,200] повторяется.
- D: серия503 исчерпывает лимит без лишнего ожидания; 200 останавливает даже если его ошибочно включили в retryable.

### Y4-M — Безопасность повтора и бюджет ожидания

Бюджет учитывает только sleep, не длительность сети; общего deadline здесь нет.

**Перенос — показать после сохранения первого решения**

Вместо503 приходит TimeoutError: сервер мог уже исполнить запрос. Для POST без серверной гарантии прекратите автоматические повторы. С гарантией повторите только с прежним ключом; бизнес-результат provider моделирует отдельно.

**Ключ для разработчика проверки**

```python
def retry_request(send, sleep, method, idempotency_supported, key, max_attempts, delay, wait_budget):
    attempts, status, waits, spent = 0, None, [], 0
    allowed = method in {"GET", "PUT", "DELETE"} or (method == "POST" and idempotency_supported and bool(key))
    stop = "attempts"
    while attempts < max_attempts:
        attempts += 1
        try:
            status = send(method, key)
        except TimeoutError:
            status = None
        if status == 200:
            stop = "success"
            break
        if status not in (503, None):
            stop = "status"
            break
        if attempts >= max_attempts:
            break
        if not allowed:
            stop = "unsafe"
            break
        if spent + delay > wait_budget:
            stop = "budget"
            break
        sleep(delay)
        waits.append(delay)
        spent += delay
    return {"attempts": attempts, "last_status": status, "waits": waits, "stop": stop}
```
PUT/DELETE идемпотентны по HTTP-семантике, хотя не являются safe-методами. Задание не приравнивает эти понятия.

**Обязательные пакеты автопроверки и рубрика**

- A: GET503→200; POST с подтверждённым ключом503→200.
- B: ключ без поддержки → unsafe; delay2/budget1 → budget; точная граница разрешена; max<=0; постоянная ошибка без sleep.
- C: timeout после исполнения POST: без гарантии один вызов/unsafe; с гарантией тот же key повторён.
- D: PUT/DELETE; чередование503/timeout; лимит попыток имеет приоритет; бюджет суммируется; успех не вызывает sleep.

Для этой карточки применяется шкала 0–4 из раздела 2; каждый перечисленный пункт — отдельный проверяемый признак.

### Y6-J — Загрузка файла частями

**Основной навык:** Python и HTTP: поток и очистка.

**Кандидату**

Напишите `upload(chunks, max_bytes: int, storage) -> int`. chunks — одноразовый итератор bytes; отдельные части могут быть пустыми. max_bytes>=0. Пустой файл → 400; фактический размер больше лимита → 413; подходящий файл → 201. При OSError во время чтения → 503. После превышения не читайте следующую часть.

storage.begin() возвращает temp с write(bytes),commit(),abort(). Все методы стенда успешны. commit сохраняет файл под серверным именем; abort удаляет временный файл. Пишите по одной части, не собирая весь файл в памяти; commit только после полного успешного чтения. При отказе после begin обязательно abort. Клиентских имён и Content-Length в сигнатуре нет: они не являются источником истины.

**Перенос — показать после сохранения первого решения**

Итератор может поднять OSError после нескольких частей. Верните503 и удалите временные данные. Переданное клиентом описание размера могло быть неверным: ограничение всегда проверяется по реально полученным bytes.

**Ключ для разработчика проверки**

```python
def upload(chunks, max_bytes, storage):
    temp = storage.begin()
    total = 0
    try:
        for chunk in chunks:
            total += len(chunk)
            if total > max_bytes:
                temp.abort()
                return 413
            temp.write(chunk)
    except OSError:
        temp.abort()
        return 503
    if total == 0:
        temp.abort()
        return 400
    temp.commit()
    return 201
```
Стенд дополнительно проверяет чередование чтения и записи. Это наблюдение протокола, не доказательство произвольной асимптотики памяти.

**Обязательные пакеты автопроверки и рубрика**

- A: одна допустимая часть → 201; несколько частей → тот же сохранённый контент.
- B: пусто/пустые части400; ровно лимит201; лимит+1→413; cleanup; max0.
- C: OSError между частями → 503, нет сохранённого или временного файла.
- D: после превышения итератор больше не читается; большая последовательность коротких частей; commit ровно один и только в конце.

Для этой карточки применяется шкала 0–4 из раздела 2; каждый перечисленный пункт — отдельный проверяемый признак.

### Y6-M — Проверка архива до публикации

**Основной навык:** Python и HTTP: потоковая валидация.

**Кандидату**

Напишите `upload_archive(chunks, content_type: str, max_bytes: int, expanded_limit: int, max_files: int, storage, inspect_archive) -> int`. Лимиты неотрицательные. Принимается только ZIP: content_type должен быть точной строкой application/zip, иначе415 **до чтения**. chunks — одноразовый итератор bytes, включая пустые части. storage.begin() возвращает temp; его write(bytes), abort() и commit() успешны. Сначала потоково загрузите сжатые bytes: пустой файл400, фактический размер больше max_bytes413, OSError во время чтения503. Считайте длину полученных частей; после превышения больше не читайте и не пишите. Не накапливайте весь файл в памяти. commit публикует архив под серверным именем; abort удаляет временные данные.

temp имеет write,abort,commit и доступен inspect_archive(temp). Этот предоставленный безопасный адаптер проверяет реальный ZIP-формат и выдаёт одноразовый поток записей {name:str,is_symlink:bool,chunks:итератор bytes}. При неправильном/повреждённом ZIP поднимает ValueError (в том числе во время обхода) →415. Вложенные архивы считаются обычными файлами, не раскрываются. Записи-каталоги отсутствуют. Распакованные байты не сохраняйте; считайте их фактическую сумму.

Недопустимый путь или ссылка →400: имя пустое, начинается с '/', содержит обратный слеш, двоеточие, пустой компонент либо компонент '.'/'..', или is_symlink=True. Повтор имени →400. Число файлов >max_files либо распакованных bytes >expanded_limit →413. На любой отказ abort, на успех commit/201. Порядок для каждой записи: имя/ссылка/повтор → число файлов → чтение и лимит распакованных bytes. На первом отказе остановитесь. Только storage выбирает имя сохранённого архива; пользовательский путь не используется.

**Перенос — показать после сохранения первого решения**

ZIP мал по сжатому размеру, но распакованные части превышают expanded_limit. Не доверяйте метаданным размера: прекратите обход при превышении и верните413. После отказа не должно остаться опубликованного или временного файла.

**Ключ для разработчика проверки**

```python
def upload_archive(chunks, content_type, max_bytes, expanded_limit, max_files, storage, inspect_archive):
    if content_type != "application/zip":
        return 415
    temp = storage.begin()
    def reject(status):
        temp.abort()
        return status
    compressed = 0
    try:
        for chunk in chunks:
            compressed += len(chunk)
            if compressed > max_bytes:
                return reject(413)
            temp.write(chunk)
        if compressed == 0:
            return reject(400)
        names, count, expanded = set(), 0, 0
        for entry in inspect_archive(temp):
            name = entry["name"]
            parts = name.split("/")
            if (not name or name.startswith("/") or "\\" in name
                    or ":" in name or any(p in ("", ".", "..") for p in parts)
                    or entry["is_symlink"] or name in names):
                return reject(400)
            names.add(name)
            count += 1
            if count > max_files:
                return reject(413)
            for chunk in entry["chunks"]:
                expanded += len(chunk)
                if expanded > expanded_limit:
                    return reject(413)
    except ValueError:
        return reject(415)
    except OSError:
        return reject(503)
    temp.commit()
    return 201
```

Ошибки ValueError относятся к адаптеру разбора ZIP, а не к произвольному вводу неуказанных типов. Политика пути намеренно строгая; это не универсальная нормализация всех файловых систем. Проверка формата ZIP принадлежит предоставленному адаптеру и не засчитывается как самостоятельно написанный парсер.

**Обязательные пакеты автопроверки и рубрика**

- A: один безопасный файл в ZIP → 201; два файла внутри каталога a/ с допустимыми именами → 201.
- B: MIME415; реальный формат415; пустой поток400; границы сжатого размера; cleanup; ../, абсолютные пути, ссылки, дубли имён400.
- C: сжатый поток в лимите, фактический распакованный размер больше expanded_limit →413; число файлов отдельно ограничено.
- D: ValueError/OSError в середине распаковки; точная граница; нарушение имени имеет приоритет над числом файлов; прекращение чтения после отказа.

Для этой карточки применяется шкала 0–4 из раздела 2; каждый перечисленный пункт — отдельный проверяемый признак.

## 6. Параметризованные варианты: данные, правила и ключ

Менять только имена недостаточно. Генератор создаёт отдельный манифест для каждого задания: `bank_version`, `task_id`, `family_id`, `target_level`, `rule_version`, `seed`, `fixture_hash`, `oracle_version`, `test_pack_version`. Seed нужен для воспроизведения, а не является секретной криптографической защитой. Ключи HMAC — исключительно тестовые. Настоящие секреты в задания не помещаются.

**Два вида варианта:**

1. Вариант данных сохраняет контракт, но меняет значения, расположение дублей, равенств и NULL, порядок страниц и точки сбоев. Генерация обязана сохранять диагностическую ситуацию: например, NULL не должен случайно исчезнуть из проверки NOT IN.

Имена вызываемых функций и поля интерфейсов остаются стабильными. Переименование предметной области — «команды» в «магазины», «счёт» в «документ» — допускается только вместе с полной согласованной редакцией текста и схемы. Случайная смена имени функции не является проверкой компетенции.

### Перенос и новая фикстура — разные свидетельства

Некоторые C-пакеты проверяют новое сочетание данных в неизменном правиле, например NULL или равные score. Это полезная проверка обобщения, но слабое свидетельство переноса. Изменение правила из таблицы выше — более сильная дополнительная проба: кандидат адаптирует сохранённое решение. Её результат фиксируется отдельно до калибровки; добавлять такие версии к итоговому баллу без обновления спецификации нельзя. Ни успешный C, ни изменение правила сами по себе не доказывают отсутствие внешней помощи.

6. Перед допуском карточки прогнать несколько независимо написанных корректных решений и набор ошибочных решений. Если допустимое решение отклоняется из-за скрытого ожидания, исправить задание/проверку и пересчитать затронутые результаты.

```json
  "bank_version": "3.0",
  "rule_version": "first_id_wins-v1",
```

| Что проверяет машина | Что требуется дополнительно |

## 8. Защита собственного решения

Предлагаемый этап после теста — проверка решения с человеком. Это **новая процедура к внедрению**, а не уже реализованная гарантия. Правила использования документации, поиска, IDE и AI сообщаются до начала. В пилоте результаты разных режимов помощи хранятся раздельно.

Проверяющий выбирает одно сохранённое решение кандидата и выполняет три действия:

1. Просит показать конкретный участок кода, отвечающий за выбранное ограничение, и предсказать результат нового маленького входа. Пример X4: «На последней странице next_cursor указывает назад. Будет ли ещё один запрос? Покажите, где это решается».
2. Меняет одно объявленное правило из таблицы параметризации. Пример Y1: «Теперь score сортируется по убыванию, id — по возрастанию. Измените сравнение с курсором». Кандидат правит собственный код; новый тест исполняется.
3. Просит назвать и продемонстрировать тест, который обнаружит конкретную ошибку. Пример X6: «Провайдер выполнил платёж и потерял ответ. Какой ID получит повторный вызов?»

Протокол содержит вопрос, исходный и изменённый код, прогноз кандидата, фактический результат и объём подсказок. Отмечаются три независимых признака: нашёл соответствующий участок; правильно предсказал поведение; внёс работающую правку. Свободное владение терминологией не заменяет эти признаки. При неоднозначном условии результат считается спорным, а не неверным. Для пограничного решения нужен второй проверяющий с тем же материалом.

Не устанавливать новый автоматический порог грейда по этим трём признакам без данных. Несовпадение с автоматическим тестом → разбор или дополнительная задача, а не безусловное обвинение в списывании. Формат должен учитывать доступность: при необходимости письменное объяснение и демонстрация правки вместо устной речи.

Время основной сессии и защиты фиксируется в пилоте отдельно: чтение, работа, перенос, технические простои. Жёсткий норматив до измерений не назначается. После пилота его выбирают с учётом распределения времени, незавершений и условий доступности. Ограничение времени не доказывает самостоятельность и не заменяет защиту.

| Угроза | Что может уменьшить риск | Чего нельзя заключать |
|---|---|---|
| Опубликован конкретный ответ | Новые правила и данные, ротация уязвимого семейства | Что знакомый алгоритм больше не поможет |
| Повторные попытки | История family_id/rule_version, раздельный учёт первого прохождения | Что новый seed — новое независимое свидетельство |
| Внешняя помощь/LLM | Прозрачные правила, изменение собственного кода на защите | Что дистанционное прохождение исключает помощника |
| Автоматизированное решение | Нестандартные открытые правила, проверка хода адаптации | Что сложная формулировка или таймер остановят автоматизацию |
| Подмена человека/профиля | Отдельная допустимая процедура идентификации и сопоставление с защитой | Что верный код устанавливает личность или опыт работы |

Junior здесь работает с заданным алгоритмическим контрактом и локальными границами. В Middle добавлены конкурирующие состояния, порядок преобразований, сбои и сохранение инварианта на изменившемся входе. Это содержательные различия задач, **не доказанное различение людей по грейду**. Если Middle проходит только за счёт узнавания знакомого шаблона, пилот должен это выявить; переименование само по себе проблему не решит.

## 10. Пилот и допуск к использованию

1. **Редакторский контроль.** Независимый специалист решает каждую карточку, видя только кандидатское условие. Любое требование, найденное только в ключе, либо переносится в условие, либо удаляется из проверки.
2. **Технический контроль.** Реализовать адаптеры и раннер; прогнать независимые корректные решения, мутанты, повторяемые сбои и все сохранённые seeds. Сохранить версии и результаты. Это подтверждает качество проверки конкретного ответа, не точность грейда.
3. **Проверка понятности.** Наблюдать чтение условий людьми целевой аудитории; записывать уточнения, неверные трактовки и время. Исправить формулировки до сбора калибровочных данных.
4. **Сбор эмпирики.** Кандидаты с независимо установленным профилем работы и пограничные кандидаты выполняют формы в сбалансированном порядке. Учитывать знакомство с заданиями, помощь и повторные попытки. Не определять «истинный Middle» по результату этого же банка.
5. **Пороги.** Независимая группа специалистов описывает минимально допустимое выполнение рабочих действий. Для практических ответов использовать анализ целостных работ (Body of Work) и сопоставление с пограничной группой; modified Angoff можно применять к ожиданиям по рубрике после обучения экспертов. Выбор порогов — отдельное исследование, не следствие среднего балла или названия карточки.
6. **Проверка решений.** Оценить расхождения людей, повторяемость, X/Y, ложные подтверждения/отказы и неопределённость около границы. Размер выборки выбирать по требуемой точности интервалов и дизайну; малую удобную выборку не объявлять достаточной заранее.
7. **Ограниченный выпуск.** До подтверждения валидности публиковать профиль выполненных задач и ограничения. Для работодателя не выдавать автоматическое «грейд подтверждён» только по этому файлу. При выпуске каждой новой версии отслеживать дрейф сложности и утечки.

| Данные | Единица наблюдения и анализ | Корректная интерпретация |
|---|---|---|
| Согласие людей по защите | Один и тот же ответ × независимые проверяющие; процент согласия, взвешенная kappa для порядковой шкалы или ICC для согласованной числовой шкалы, с интервалами | Не смешивать с детерминированным совпадением автотестов; малая выборка даёт широкую неопределённость |
| Повторяемость | Один человек × две независимые попытки/версии, с интервалом; изменения балла и решения | Повтор на знакомом задании содержит эффект обучения |
| X/Y | Люди × формы с рандомизацией порядка или якорями; разность средних и решений, интервалы, эффект порядка | «Нет значимой разницы» не доказывает эквивалентность; предел допустимой разницы задаётся заранее |
| Различение | Человек × задание × независимый рабочий критерий; распределения пакетов/баллов и связь с критерием | Корреляция с итогом, куда включён сам item, завышает связь |
| Ложные подтверждения/отказы | Решение системы × независимое решение специалистов; confusion matrix, доли с биномиальными интервалами | Без независимого критерия точность неизвестна; его собственные ошибки тоже учитываются |
| Утечка/знакомство | Человек × история экспозиции × версия; сравнение первых и повторных прохождений с контролем опыта | Нельзя приписать причинность одному росту балла без подходящего дизайна |
| Время/незавершения | Человек × карточка × этап × технический простой | Нужны распределения и причины незавершений, не только среднее время успешных |
