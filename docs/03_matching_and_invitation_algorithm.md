# Спецификация `docs/03_matching_and_invitation_algorithm.md`

## Граница MVP

По согласованному объёму [06_plan.md](06_plan.md) подбор по подтверждённым категориям работает для Backend Junior и Backend Middle. Frontend доступен только как направление будущего расширения, без обязательной демонстрационной задачи и без подтверждённой frontend-категории. Для такой потребности интерфейс сообщает, что оценивание направления пока не поддерживается.

В MVP используется самостоятельная оценка; AI-режим — будущая возможность. Профиль заполняется вручную, без распознавания резюме и runtime ML/NLP. Формула рейтинга, объяснения, зарплата, приглашения и приватность не меняются.


Документ описывает основную механику критерия **«Новая механика подбора — 35%»**: работодатель формулирует потребность, получает объяснимую подборку по подтверждённым навыкам и сам направляет кандидату предложение с зарплатой.

Основание: §2, §2.1, §2.2 и §6 ТЗ, а также обновлённая механика оценки из `02_assessment_algorithm.md`.

Первая версия алгоритма полностью детерминированная: **проверка доступа → фильтры → взвешенная оценка → объяснения → приглашение → согласие кандидата**. Документ является спецификацией, а не отчётом о готовой реализации.

## 1. Роль работодателя и продуктовый сценарий

Работодатель регистрируется с подтверждением email и заполняет профиль компании:

- Название и описание.
- Направление деятельности.
- Описание команды.
- Контакт представителя компании.

Верификация компании не обязательна для MVP. Статус «проверена» нельзя показывать без соответствующей процедуры.

Основной сценарий:

1. Работодатель описывает задачу команды и необходимые компетенции.
2. Указывает специализацию, допустимые грейды, технологии и условия.
3. Получает подборку по категориям с объяснениями.
4. Просматривает доказательства навыков и сохраняет интересующих кандидатов.
5. При необходимости меняет условия и сравнивает новую подборку с предыдущей.
6. Выбирает конкретного человека и отправляет предложение с зарплатой.
7. Кандидат принимает или отклоняет предложение.
8. После принятия открываются разрешённые кандидатом контакты.

**Публикация вакансии не требуется ни для подбора, ни для приглашения.** Она остаётся дополнительным сценарием.

Отличительная ценность: работодатель выбирает по доказательствам навыков, нужных именно его команде, и сразу предлагает совместимые условия. Инициатива работодателя сама по себе уже предложена в ТЗ; оригинальность решения показывается связью «задача команды → подтверждённые сильные стороны → объяснение места → предложение».

Обязательный демопример: два кандидата одной категории с разными профилями SQL и HTTP/API. При одинаковых остальных компонентах смена повышенного приоритета с SQL на HTTP/API меняет порядок. Объяснение показывает фактическую причину и сохраняет предыдущую подборку. Этот специально подготовленный пример демонстрирует поведение; качество ранжирования доказывается отдельно на контрольном наборе.

## 2. Модель `EmployerNeed`

Это продуктовая модель потребности, а не схема базы данных.

| Поле | Содержание и правило |
|---|---|
| `employer_id` | Владелец потребности |
| `title` | Краткое название задачи найма |
| `specialization` | Одна специализация из справочника |
| `accepted_grades` | Один или несколько явно выбранных грейдов |
| `role` | Функция человека в команде |
| `required_stack` | Обязательные технологии |
| `preferred_stack` | Желательные технологии |
| `skill_priorities` | Проверяемые навыки, важные для задачи; обычный или повышенный приоритет |
| `work_formats` | Допустимые форматы: удалённо, гибрид, офис |
| `location` | Место работы для офиса или гибрида |
| `salary_from`, `salary_to` | Обязательный диапазон перед запуском подбора |
| `salary_currency` | RUB |
| `salary_basis` | Для baseline — месячная сумма до вычета налогов |
| `team_description` | Команда, продукт и рабочее окружение |
| `task_description` | Что предстоит делать кандидату |
| `urgency` | Срочно, обычный поиск, гибкий срок |
| `desired_start_date` | Желаемая дата выхода; обязательна при срочном поиске |
| `start_date_required` | Является ли дата выхода обязательным ограничением |
| `additional_requirements` | Структурированные требования и отдельные текстовые пожелания |
| `vacancy_id` | Необязательная связь с опубликованной вакансией |
| `version` | Версия условий |

Для каждой технологии работодатель выбирает, достаточно ли указания в профиле или требуется подтверждение оценкой.

Правила:

- `salary_from > 0`, `salary_to ≥ salary_from`.
- Технологии нормализуются по справочнику: например, `Python` и `python` — одно значение.
- Указание Django или FastAPI не означает автоматически подтверждённый Python.
- Свободный текст не превращается в скрытые фильтры. Значимые требования работодатель подтверждает в структурированных полях.
- Если приоритеты навыков не выбраны, используются тематические веса соответствующей категории из документа оценки.
- Зарплаты с разными основаниями расчёта не сравниваются автоматически.
- Несколько грейдов формируют отдельные категории. Их тестовые результаты не смешиваются в единую шкалу.

### 2.1. Три шаблона потребности — MVP

Использовать три уже подготовленных описания вакансий как редактируемые стартовые шаблоны формы EmployerNeed:

| Шаблон | Предлагаемые повышенные приоритеты |
|---|---|
| Разработка API и проверка входных данных | HTTP/API; безопасность/валидация |
| Работа с SQL и отчётами | SQL/данные |
| Интеграции и обработка сбоев | HTTP/API; отладка/надёжность |

Шаблон заполняет описание и приоритеты навыков (2 вместо обычного 1), но работодатель видит, редактирует и подтверждает все значимые поля, включая грейд, технологии и зарплату. Бюджет и требование подтверждения конкретной технологии не угадываются. Любую потребность можно создать без шаблона.

Шаблоны не создают скрытых фильтров, не меняют пороги грейда, тестовый blueprint или формулу рейтинга. Сохранять код и версию шаблона как происхождение данных; уже сохранённая потребность не изменяется при обновлении шаблона. Runtime NLP и генерация вакансий не нужны.

## 3. Допуск кандидатов и hard filters

### 3.1. Проверки до ранжирования

| Условие | Правило |
|---|---|
| Приватность | Кандидат разрешил появляться в поиске и получать предложения от этого работодателя |
| Специализация | Совпадает с потребностью |
| Грейд | Входит в явно выбранные грейды |
| Категория | Получена по результатам оценки, а не из резюме |
| Статус оценки | Есть действующее опубликованное подтверждение по правилам `02_assessment_algorithm.md` |
| Режим оценки | Самостоятельный грейд не заменяется результатом работы с AI |
| Обязательный стек | Присутствуют все обязательные технологии с требуемым типом подтверждения |
| Обязательные навыки | Если потребность требует конкретного подтверждённого умения, соответствующее доказательство должно присутствовать |
| Зарплата | Диапазоны совместимы |
| Формат работы | Есть хотя бы один общий допустимый формат |
| Локация | Совместима, когда требуется присутствие |
| Дата выхода | Соблюдается, если работодатель отметил её обязательной |
| Дополнительные требования | Применяются только явно формализованные обязательные условия |

Неподтверждённый грейд, запрет видимости и отсутствие обязательной технологии не компенсируются высоким рейтингом.

Неуспешная новая попытка тестирования сама по себе не отменяет ранее действующее подтверждение. Matching использует опубликованный статус из системы оценки, а не интерпретирует историю попыток самостоятельно.

### 3.2. Зарплатная совместимость

При известных диапазонах:

**Совместимость существует, если максимальная нижняя граница не превышает минимальную верхнюю границу.**

Пересечение на одной сумме допустимо. Если кандидат указал только минимальную приемлемую сумму, достаточно, чтобы верхняя граница предложения была не ниже неё.

В объяснении показывать «диапазоны пересекаются», если совпадение частичное. Не утверждать, что весь диапазон работодателя устраивает кандидата.

Скрытые от работодателя ожидания можно использовать только при согласии кандидата на такую проверку. Точную скрытую сумму не раскрывать.

### 3.3. Неизвестные условия

Зафиксирован выбранный подход:

- **«Условия совместимы»** — основная подборка.
- **«Нужно уточнить условия»** — отдельная группа.

Во вторую группу попадают кандидаты без данных о зарплате, формате или сроке выхода, если по известным данным противоречий нет.

Отсутствие даты выхода не является пробелом, если срок работодателю не важен.

Известная несовместимость не переносится в группу уточнения. Неподтверждённые кандидаты также не попадают туда.

Приглашение кандидату из второй группы разрешено, но интерфейс явно показывает работодателю непроверенные условия.

## 4. Детерминированное ранжирование

### 4.1. Формула baseline

Ранжировать кандидатов **внутри одной категории и одной группы совместимости**:

**Score = clamp(55 × T + 25 × K + 8 × A + 7 × F + 5 × U − P, 0, 100).**

Все компоненты, кроме штрафа, находятся в диапазоне 0–1.

| Компонент | Значение |
|---|---|
| `T` | Подтверждённые навыки применительно к потребности |
| `K` | Совпадение технологий с учётом подтверждения |
| `A` | Соответствие желаемому сроку выхода |
| `F` | Наличие подтверждённых достижений ФСП |
| `U` | Свежесть доказательств по нужным навыкам |
| `P` | Штраф за давно не подтверждавшиеся условия поиска |

Веса — начальная гипотеза для проверки, а не доказанный оптимум. Балл не является вероятностью успешного найма.

### 4.2. Подтверждённые навыки — `T`

Для каждого навыка из потребности взять нормализованную оценку из системы тестирования.

**T = сумма(приоритет навыка × оценка навыка) / сумма приоритетов.**

- Оценка переводится из 0–100 в 0–1.
- Повышенный приоритет имеет вес 2, обычный — 1.
- Непроверенный дополнительный навык получает 0 как отсутствие доказательств, а не как доказательство некомпетентности.
- Требуемый обязательный подтверждённый навык проверяется до ранжирования.
- Результаты с AI не повышают оценку самостоятельного навыка.
- Несопоставимые версии методик нельзя напрямую усреднять. Используется утверждённое системой оценки соответствие; без него результат обозначается как отсутствующий для расчёта.

Так кандидат с подходящим профилем сильных сторон может оказаться выше кандидата с более высоким общим тестовым баллом. Подтверждение Backend Middle на Python не подтверждает JavaScript или иной язык: проверенные технологии берутся только из SkillEvidence, остальные остаются самоописанием.

### 4.3. Совпадение стека — `K`

Учитывать только технологии, запрошенные работодателем.

Вес обязательной технологии — 2, желательной — 1.

Коэффициент подтверждения:

- 1 — технология проверена оценкой.
- 0,6 — указана кандидатом, но не проверена.
- 0 — отсутствует.

**K = сумма(вес технологии × коэффициент) / сумма весов технологий.**

Если стек не задан, `K = 1` для всех: компонент не влияет на порядок.

Добавление десятков посторонних технологий в резюме не увеличивает балл. Для обязательной технологии с требованием подтверждения коэффициент 0,6 недостаточен для прохождения фильтра.

### 4.4. Доступность — `A`

Если дата выхода не важна, `A = 1` для всех.

Если дата задана:

- Выход не позже желаемой даты: `A = 1`.
- Задержка на `d` дней: `A = max(0, 1 − d / 30)`.
- Дата неизвестна: `A = 0`, кандидат находится в группе уточнения.

Если дата обязательна, известное опоздание исключается фильтром ещё до расчёта.

### 4.5. ФСП — `F`

- `F = 1` при наличии хотя бы одного достижения с проверенным происхождением и принадлежностью.
- `F = 0` при отсутствии истории или подтверждения.

Количество одинаковых записей и повторное добавление достижений бонус не увеличивают. Отсутствие истории ФСП не препятствует показу.

В хакатонной демонстрации тестовые подтверждения используются только в явно обозначенном наборе демонстрационных данных.

### 4.6. Актуальность — `U` и `P`

`U` рассчитывается по нужным работодателю навыкам с теми же приоритетами:

- Подтверждение не старше 90 дней — 1.
- От 91 до 180 дней — 0,5.
- Старше 180 дней или доказательств нет — 0.

Учитываются результаты основной оценки и допустимых независимых регулярных заданий. Редактирование резюме не обновляет дату проверки навыка.

`P` зависит от последнего явного подтверждения кандидатом своих условий поиска:

- До 90 дней — 0.
- От 91 до 180 дней — 3.
- Старше 180 дней или дата отсутствует — 5.

Вход на сайт и косметическое редактирование профиля не сбрасывают штраф.

### 4.7. Что не даёт бонусов

Не использовать в baseline отдельный `score_profile_completeness`. Длина резюме, фотография и раскрытие дополнительных личных сведений не доказывают пригодность.

Полноту обязательных сведений показывать как качество данных и использовать для определения группы совместимости.

Зарплатная совместимость — фильтр. Более низкие ожидания не дают преимуществ в ранжировании.

### 4.8. Стабильность результата

При одинаковых входных данных порядок одинаков:

1. Итоговый балл.
2. `T`.
3. `K`.
4. Стабильный ключ пары «потребность — кандидат».

Сохранить версию формулы, версию потребности, дату расчёта и использованные подтверждения.

Не скрывать кандидатов только из-за низкого итогового балла, если они прошли обязательные фильтры.

## 5. Explainability и работа с подборкой

Каждая карточка содержит:

- Подтверждённую категорию и экспериментальный статус методики.
- Границы оценки: Python, проверенные SQL/data- и HTTP/API-навыки, формат проверки; другие языки и производственный опыт автоматически не подтверждены.
- Два-три наиболее существенных основания высокого места.
- Совместимые условия.
- Существенные непроверенные сведения.
- Безопасные основания подтверждения по §2.8.1 документа 02; без отдельного бонуса за обнаруженные ошибки.

Пример:

> Подтверждён Backend Middle. Сильные результаты по SQL и обработке ошибок API — эти навыки отмечены как приоритетные. В профиле есть 4 из 5 нужных технологий, 3 подтверждены оценкой. Зарплатные диапазоны пересекаются. Срок выхода нужно уточнить.

Правила:

- Объяснения формируются шаблонами из фактических данных.
- Причина допуска и причина высокого места различаются: зарплатное пересечение разрешает показ, но не добавляет баллы.
- «Есть достижения ФСП» используется только с корректным статусом источника.
- «Профиль обновлён недавно» не заменяет точное «условия поиска подтверждены 10 дней назад».
- Отсутствие проверки навыка обозначается прямо.
- По запросу можно открыть составляющие балла и основания подтверждений.

Работодатель может сохранять кандидатов, скрывать неинтересных в рамках конкретной потребности и отмечать причины. Эти отметки не изменяют общий рейтинг человека для других работодателей.

Изменение фильтров создаёт новую версию подборки. Предыдущая остаётся доступной для сравнения.

Сохранённые подборки не обходят актуальные настройки доступа. Если кандидат закрыл видимость, вместо старой карточки отображается нейтральная отметка о недоступности.

При пустой выдаче система предлагает явно изменить условия. Согласие кандидата, подтверждение грейда и приватность автоматически не ослабляются.

### 5.1. Сравнение двух кандидатов по одной потребности — MVP

Работодатель выбирает ровно две доступные карточки из одной версии подборки, одной категории и одной группы совместимости. Веб-клиент показывает таблицу на основе существующих безопасных данных выдачи:

| Строка сравнения | Что показать |
|---|---|
| Приоритетные навыки потребности | Сопоставимые результаты и краткое основание подтверждения |
| Требуемые технологии | Подтверждена / только указана / не проверена / отсутствует по имеющимся данным |
| Условия | Совместимы / требуют уточнения, без раскрытия скрытых ожиданий |
| Основания результата | Семейства доказательств, дата, версия и экспериментальный статус; безопасная сводка проверки решений |
| Итоговое место | Существующий балл и его компоненты, без новой формулы «победителя» |

Числа сравниваются только при сопоставимых версиях методики; иначе показываются текстовые ограничения. Результат одного этапа не объявляется общей квалификацией. Непроверенный навык не подписывается «не умеет». Закрытые задания, ответы и реализации для проверки тестов не выдаются.

Доступ проверяется заново при открытии сравнения через существующее чтение подборки. При скрытии профиля соответствующая колонка становится недоступной; сохранённые снимки не обходят приватность. Сравнение не раскрывает контакты до согласия и не меняет общий рейтинг кандидата. Отдельный сервис сравнения не нужен.

## 6. Invitation flow

1. Работодатель выбирает кандидата.
2. Система проверяет актуальную видимость, категорию и возможность отправки.
3. Работодатель заполняет:
   - Описание предложения.
   - Зарплату «от–до» в рублях.
   - Формат и существенные условия работы.
   - Способ связи с представителем компании.
4. Название компании подставляется из профиля.
5. По умолчанию используются условия потребности; индивидуальное предложение можно уточнить.
6. Перед отправкой повторно проверяется совместимость известных условий.
7. Сохраняется приглашение `sent` с неизменяемой копией отправленных условий.
8. Кандидат получает уведомление и просматривает предложение.
9. Кандидат принимает или отклоняет.
10. При принятии открываются выбранные им контакты конкретному работодателю.

Принятие означает готовность продолжить общение по предложенным условиям.

Правила:

- Приглашение не требует опубликованной вакансии.
- Изменение потребности не переписывает уже отправленное предложение.
- Для исправления предложения работодатель отзывает его и отправляет новое.
- Повторная отправка одного действия не создаёт дубликат.
- Для пары «работодатель — потребность — кандидат» допускается одно активное приглашение.
- После принятия повторное приглашение по той же потребности не требуется.
- Отклонённое приглашение не запускает автоматическую повторную рассылку.
- Кандидат может запретить дальнейшие приглашения от работодателя.

Для неизвестных условий приглашение содержит конкретное предложение, но система не заявляет предварительную совместимость.

## 7. Модель статусов

Срок действия по умолчанию — **7 суток с момента отправки**.

| Статус | Значение | Допустимые переходы |
|---|---|---|
| `sent` | Приглашение отправлено | `viewed`, `accepted`, `rejected`, `expired`, `withdrawn` |
| `viewed` | Кандидат открыл предложение | `accepted`, `rejected`, `expired`, `withdrawn` |
| `accepted` | Кандидат согласился продолжить общение | Конечный статус приглашения |
| `rejected` | Кандидат отказался | Конечный |
| `expired` | Срок ответа закончился | Конечный |
| `withdrawn` | Работодатель отозвал предложение | Конечный |

`viewed` устанавливается при открытии кандидатом, а не при доставке уведомления или просмотре почтовым роботом.

Если время истекло, принять приглашение нельзя, даже если обновление статуса ещё не отобразилось в интерфейсе.

При одновременном принятии и отзыве успешно завершается только один допустимый переход. Обе стороны получают фактический итог.

Отзыв разрешён только до принятия. Отзыв доступа к контактам после принятия — отдельное действие кандидата; он не переписывает историю приглашения.

## 8. Приватность и доступ

- Кандидат видит только адресованные ему приглашения.
- Работодатель видит только принадлежащие ему потребности, подборки и приглашения.
- В baseline один аккаунт работодателя управляет своим профилем компании; коллективный доступ отдельно не вводится.
- До принятия не выдаются телефон, email, мессенджеры, исходное резюме и вложения с контактами.
- Ограничение действует в карточках, PDF, выгрузках и любых способах получения данных.
- Уведомления о принятии не должны содержать копию контактов: доступ проверяется при открытии.
- Принятие открывает разрешённые контакты только отправившему предложение работодателю.
- Для самостоятельного отклика применяется отдельное аналогичное согласие в рамках дополнительного сценария вакансий.
- Доступ одного работодателя не распространяется на остальных.
- Отзыв согласия закрывает будущий доступ, но не может гарантировать удаление уже увиденной информации.
- Зарплата обязательна в каждом приглашении и опубликованной вакансии.

Отключение появления в поиске прекращает новые показы и приглашения. Уже полученные предложения остаются доступны кандидату для ответа, если работодатель не заблокирован.

## 9. Пограничные случаи

| Ситуация | Поведение |
|---|---|
| Нет подходящих кандидатов | Показать отсутствие результатов, отдельно — группу уточнения; предложить изменить конкретные условия |
| Нет истории ФСП | Полноценное участие в подборе; бонус равен нулю |
| Недавно изменился грейд | Использовать опубликованную категорию; пересчитать новые подборки, отметить изменение в сохранённых |
| После подбора изменились условия кандидата | Перед отправкой повторно проверить совместимость |
| После отправки изменился профиль | Условия приглашения сохраняются; актуальные данные показываются отдельно |
| Зарплата кажется низкой | Сообщить о совместимости с доступными ожиданиями; без внешних данных не называть диапазон «ниже рынка» |
| Весь бюджет ниже известных ожиданий | Не показывать несовместимых как подходящих; предложить пересмотреть условия |
| Зарплатный диапазон пересекается только частично | Показать частичное пересечение; уточнить индивидуальное предложение |
| Дубли профилей | Устранять только подтверждённые дубли одного человека; похожие имена не являются основанием объединения |
| Повторный клик отправки или принятия | Один результат без дублирования приглашения или доступа |
| Работодатель не верифицирован | Не блокировать только по этому признаку; не показывать ложный статус проверки |
| Подозрение на недобросовестность | Жалоба и проверка; автоматического обвинения по слабому сигналу нет |
| Подтверждённая блокировка работодателя | Прекратить новые действия, закрыть доступ; незавершённые приглашения отозвать с системной причиной |
| Фиктивная вакансия | Для MVP описать концепцию проверки компании, жалоб, модерации и санкций |
| Профиль давно не обновлялся | Применить ограниченный штраф и показать дату актуальности, не изменяя грейд |
| Есть только AI-оценка | Не считать её самостоятельным подтверждением категории |
| Результат оценки находится на проверке | Следовать статусу опубликованного подтверждения; спорная попытка не повышает позицию |

## 10. Валидация, метрики и приёмка

### 10.1. Контрольный набор

Подготовить разнообразные потребности и профили:

- Четыре исходные категории.
- Разные обязательные и желательные технологии.
- Полные, частичные и отсутствующие подтверждения.
- Совместимые, несовместимые и неизвестные условия.
- Профили с ФСП и без него.
- Разную актуальность и доступность.
- Проверки приватности и дубликатов.

Эксперты размечают пары до просмотра рейтинга: «релевантен», «нужно уточнение», «нерелевантен». Эталон не вычисляется той же формулой, которую предстоит проверять.

Для нескольких грейдов метрики рассчитываются по паре «потребность — категория», затем усредняются с явным указанием способа.

### 10.2. Метрики

| Метрика | Определение |
|---|---|
| `precision@10` | Число релевантных кандидатов в первых 10 позициях / 10 |
| `recall@20` | Число релевантных в первых 20 / общее число релевантных в контрольном доступном пуле |
| Релевантность фактически показанных | Релевантные / число показанных; отдельно от `precision@10` |
| Acceptance rate | Принятые приглашения / все отправленные в когорте с завершившимся сроком ответа |
| Корректность объяснений | Доля утверждений, соответствующих данным и расчёту |
| Полезность объяснений | Способность работодателя правильно назвать основания рекомендации и непроверенные условия |
| Время до подборки | Время от подтверждения заполненной потребности до готовой выдачи; p50 и p95 |
| Полное время сценария | От создания потребности до первого приглашения |

Определения precision и recall опираются на стандартную оценку поиска: [Stanford IR — precision и recall](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-unranked-retrieval-sets-1.html).

Если результатов меньше 10, не менять знаменатель `precision@10` незаметно: рядом показывать размер выдачи и точность среди фактически показанных.

Если релевантных кандидатов нет, `recall@20` обозначать как неприменимый. Без полной разметки контрольного пула recall не заявлять.

Приглашения `withdrawn`, `rejected` и `expired` остаются в знаменателе acceptance rate. Незавершённые когорты не смешиваются с завершёнными. Принятие не считается трудоустройством.

### 10.3. Сравнение алгоритмов

Сравнить на одном контрольном наборе:

1. Только hard filters и стабильный порядок.
2. Фильтры и совпадение стека.
3. Полную формулу с доказательствами навыков.

Сравнение B0/B1/B2 — обязательная часть P0, а не дополнение после интерфейса. До расчёта выдачи фиксируется разметка команды по протоколу документа 04; отсутствие внешних экспертов раскрывается.

Веса настраиваются на отдельной части данных. Контрольная выборка не используется для подбора удобных коэффициентов.

Измерять вклад ФСП, актуальности и доступности отдельно. Дополнительный компонент сохраняется, если его польза объяснима и проверяема.

### 10.4. Сценарии приёмки

- Каждый из трёх шаблонов заполняет ожидаемые поля; редактирование и создание без шаблона доступны.
- Шаблон не добавляет скрытые ограничения и не меняет тест или веса формулы.
- Сравнение двух кандидатов совпадает с данными одной версии выдачи и повторно проверяет доступ.
- Непроверенное явно отличается от подтверждённого; закрытые материалы не попадают в таблицу сравнения.


- Неподтверждённый грейд не проходит фильтр.
- Отсутствующая обязательная технология исключает кандидата.
- Отсутствующая желательная технология только влияет на порядок.
- Неизвестные условия дают отдельную группу.
- Кандидат без ФСП может занимать первое место.
- Зарплатные границы и частичное пересечение обрабатываются корректно.
- Изменение приоритетов навыков предсказуемо меняет порядок.
- Одинаковые данные дают одинаковую выдачу.
- Объяснения соответствуют расчёту и источникам подтверждений.
- Уточнение условий сохраняет предыдущую подборку.
- Сохранённая подборка не обходит приватность.
- Без зарплаты нельзя отправить приглашение или опубликовать вакансию.
- Все переходы статусов и конфликт принятия с отзывом обработаны.
- Контакты раскрываются только после разрешённого события и только нужному работодателю.
- Дубликаты действий не создают повторных приглашений.
- Истечение срока и отзыв согласия не оставляют лишнего доступа.

После MVP: проверка влияния шаблонов и сравнения на реальные решения работодателей, связь рекомендаций с результатами найма и расширение набора шаблонов. Улучшение найма не заявляется по одной демонстрации.

Документ считается готовым после описания всех десяти областей, точных правил формулы и состояний, а также проверяемого сквозного сценария. Микросервисы, схема базы данных и код в этот этап не входят.

## 11. Быстрая проверка подбора на данных жюри — обязательный MVP

### 11.1. Назначение и границы

Жюри может передать свой набор заранее оценённых кандидатов и потребностей и получить подборку без регистрации, почты, прохождения A/B и запуска runner. Это отдельная служебная проверка алгоритма подбора, а не способ получить подтверждённый грейд в продукте.

Вход загружается из локального JSON в память отдельного процесса. Команда использует те же фильтры, формулу, группировку, объяснения и правила равенства баллов, что и обычный matching. Дублировать алгоритм или упрощать его для демонстрации нельзя. База реальных пользователей не читается и не изменяется; приглашения, почта, PDF-сертификаты и публикация профилей не запускаются. Публичный endpoint импорта не нужен.

Обозначение во всех выходных файлах: **«Тестовый набор; категории и доказательства заданы во входном файле, сервисом не подтверждены»**. Такие записи никогда не превращаются в реальные SkillEvidence или подтверждения категории. Внутри тестового процесса `fixture_confirmed` моделирует допуск уже оценённого кандидата; `unconfirmed` проверяет его исключение по обычным правилам.

### 11.2. Контракт входа `matching-fixture-v1`

Поставить вместе с кодом JSON Schema `fixtures/jury/dataset.schema.json`, отдельную схему разметки, словарь идентификаторов и готовый пример. Точная машинная схема и адаптер должны соответствовать правилам этого раздела. Формат MVP — UTF-8 JSON, без загрузки архивов, CSV, PDF или исполнения кода. Тексты резюме/вакансий разрешены как описание, но не заменяют структурированные поля и не используются для скрытого извлечения навыков.

| Блок | Обязательные поля и смысл |
|---|---|
| Корень | `schema_version="matching-fixture-v1"`, `dataset_id`, `as_of` (UTC ISO 8601), `candidates`, `needs` |
| Кандидат | Уникальный `candidate_id`; `specialization`; `grade` (`junior`/`middle`); `category_status` (`fixture_confirmed`/`unconfirmed`); `assessment_scope`; `skills`; `technologies`; `fsp_verified`; `conditions`; `visibility` |
| Область оценки | `assessment_scope`: `language`, `method_version`, `format`; поддерживаемый формат баллов — `jury-skill-100-v1`, обозначающий явно заданную шкалу 0–100, а не нашу научную калибровку |
| Навыки | `skills`: объект по идентификатору навыка; значение содержит `score` 0–100, `verified_at` (UTC), `mode="independent"`. Для `unconfirmed` список доказательств пуст. Допустимые ключи: `language_algorithms`, `sql_data`, `http_api`, `debug_reliability`, `security_validation` |
| Технологии | `technologies`: объект по справочному коду; значение `verified` или `self_reported`. Статус `verified` допустим только при `fixture_confirmed` и согласованной области оценки. Само наличие технологии в резюме не подтверждает её |
| Условия | `conditions`: `salary_from`, `salary_to` (RUB в месяц до налогов), `work_formats`, `location`, `available_from`, `confirmed_at`. Неизвестное значение — явный `null`, не ноль и не автоматически подставленная дата |
| Видимость | `visibility`: `consent_to_match` (boolean), `blocked_employer_ids` (список). Это моделируемые условия набора, не согласия реальных людей |
| Потребность | Уникальный `need_id`, `employer_id`, `title`, `specialization`, `accepted_grades`, `required_stack`, `preferred_stack`, `skill_priorities`, `required_verified_skills`, `work_formats`, `location`, `salary_from`, `salary_to`, `desired_start_date`, `start_date_required` |
| Стек потребности | `required_stack` — список объектов `{technology, verification_required}`; `preferred_stack` — список кодов технологий. `skill_priorities` — объект «код навыка → 1 или 2»; `required_verified_skills` — список обязательных подтверждённых навыков |

`format="jury-skill-100-v1"` задаёт входную нормализованную шкалу, `method_version` фиксирует происхождение оценки. В одном наборе поддерживается одна явно объявленная сопоставимая версия методики. Неизвестные версии шкалы отклоняются с описанием требуемого преобразования; балл не вычисляется из названия грейда. Другая исходная шкала требует заранее описанного преобразования до импорта, которое фиксируется в паспорте набора и не использует метки релевантности.

MVP поддерживает категорию backend junior/middle, кодовые доказательства на Python и предусмотренные SQL/HTTP-навыки. Неподдерживаемые специализации, грейды и области оценки не переименовываются в backend/Python: импорт сообщает ошибку и ограничение. Другие технологии из справочника могут быть указаны как самоописание; подтверждать их Python-тестом нельзя. Сценарии отказа в неподдерживаемой категории остаются отдельными негативными тестами.

Справочник v1 задаёт `specialization="backend"`, язык `python`, форматы работы `remote`/`hybrid`/`office`; коды технологий и их допустимые алиасы поставляются вместе с примером. `location` — согласованный строковый код места или `null`, без географических догадок; даты выхода — YYYY-MM-DD. Булевы значения не принимаются как числа баллов. Все обязательные поля присутствуют, даже если допустимое значение — `null`.

Успешный импорт требует заполнения обязательных полей. Необязательные описательные поля `EmployerNeed` могут отсутствовать: адаптер использует документированные нейтральные значения (пустой текст, `vacancy_id=null`, `version=1`, `urgency="обычный поиск"`); они не добавляют фильтров. Пустые приоритеты используют текущий blueprint; отсутствие предпочтительного стека передаётся пустым списком. Неизвестные условия обрабатываются по §3, без дополнительного «штрафа импорта».

### 11.3. Минимальный пример входа

Пример демонстрирует формат, а не измеренное качество; одного кандидата недостаточно для содержательной оценки ранжирования. Перед сдачей подготовить расширенный пример с разным порядком при смене SQL/HTTP-приоритета, неподтверждённым кандидатом, неизвестной зарплатой и запретом видимости.

```json
{
  "schema_version": "matching-fixture-v1",
  "dataset_id": "jury-example",
  "as_of": "2026-10-07T09:00:00Z",
  "candidates": [{
    "candidate_id": "c1", "specialization": "backend", "grade": "middle",
    "category_status": "fixture_confirmed",
    "assessment_scope": {"language": "python", "method_version": "jury-example-v1", "format": "jury-skill-100-v1"},
    "skills": {
      "sql_data": {"score": 80, "verified_at": "2026-10-01T09:00:00Z", "mode": "independent"},
      "http_api": {"score": 70, "verified_at": "2026-10-01T09:00:00Z", "mode": "independent"}
    },
    "technologies": {"python": "self_reported", "sql": "verified", "http_api": "verified"},
    "fsp_verified": false,
    "conditions": {"salary_from": 150000, "salary_to": 200000, "work_formats": ["remote"], "location": null, "available_from": "2026-10-15", "confirmed_at": "2026-10-01T09:00:00Z"},
    "visibility": {"consent_to_match": true, "blocked_employer_ids": []}
  }],
  "needs": [{
    "need_id": "n1", "employer_id": "e1", "title": "SQL и отчёты",
    "specialization": "backend", "accepted_grades": ["middle"],
    "required_stack": [{"technology": "python", "verification_required": false}],
    "preferred_stack": ["sql"],
    "skill_priorities": {"sql_data": 2, "http_api": 1},
    "required_verified_skills": ["sql_data"],
    "work_formats": ["remote"], "location": null,
    "salary_from": 160000, "salary_to": 220000,
    "desired_start_date": "2026-10-20", "start_date_required": false
  }]
}
```

Код `sql` со статусом `verified` требует наличия доказательства `sql_data`, `http_api` — одноимённого навыка, `python` — `language_algorithms` и `assessment_scope.language="python"`. Эту явную карту поддерживает схема/адаптер. Категория в fixture задана внешним источником, а не вычислена из полноты этого примера: импорт не является тестом правил присвоения грейда. Неполные доказательства не достраиваются и учитываются matching как отсутствующие.

### 11.4. Разметка пар хранится отдельно

Необязательный `labels.json` содержит `schema_version="matching-labels-v1"`, `dataset_id`, `pairs`. Каждая пара: `need_id`, `candidate_id`, `relevance` от 0 до 3 и `eligibility` (`eligible`, `needs_clarification`, `excluded`) по независимой разметке. Для примера: `{"need_id":"n1","candidate_id":"c1","relevance":3,"eligibility":"eligible"}`. Дубли пар и ссылки на отсутствующие записи — ошибка.

Matching получает только `dataset.json`. Загрузку labels выполняет отдельный этап после формирования выдачи. Даже при одной общей команде эталон не передаётся в алгоритм и не используется для выбора весов, нормализации или фильтров. Отсутствие метки не означает `relevance=0`.

Без разметки сохраняются выдача и объяснения, а метрики помечаются «не измерено». При неполной разметке для потребности основные Precision@10, Recall@20 и nDCG@10 также не рассчитываются: отчёт перечисляет пропущенные пары. Полнота проверяется по всем кандидатам входного пула, включая исключённых, чтобы ошибка фильтра не скрыла релевантный профиль. Эталонный допустимый пул определяется `eligibility` из labels, а не результатом фильтра проверяемого алгоритма. Ошибки допуска и блокировки приватных профилей показываются отдельно; исключённый по эталону кандидат в выдаче не считается релевантным даже при высоком relevance. Группу уточнения показывать отдельно. Правила короткой выдачи, нулевого числа релевантных и расчёта метрик — документ 04, §3.2.

### 11.5. Запуск, выход и ошибки

Контракт команд для реализации в MVP (написание этой спецификации ещё не означает готовность программы):

```bash
python -m app.tools.matching_check --write-example ./jury-example
python -m app.tools.matching_check --input ./jury-example/dataset.json --validate-only
python -m app.tools.matching_check --input ./jury-example/dataset.json --labels ./jury-example/labels.json --output ./jury-result
```

Первый вызов создаёт обе схемы, словарь кодов, валидные примеры dataset/labels и короткую инструкцию. Второй проверяет вход без расчёта выдачи. Третий валидирует, импортирует в память, запускает B0/B1/B2 и формирует отчёт. `--labels` можно не указывать. Команда доступна в установленном приложении и в поставляемом образе; README должен содержать точную команду запуска образа с входной папкой read-only и выходной папкой для отчёта. Для этого режима не нужны PostgreSQL, почта, runner, внешний API или секреты; модули не должны подключать их при импорте.

Выход: `rankings.json` (по потребности, категории и группе), `metrics.json`, `report.md`, `run_manifest.json`. Сохранять ID, порядок, компоненты балла, объяснения и причины исключения; объяснения не раскрывают скрытые зарплатные ожидания в обычном интерфейсе. Полный служебный отчёт доступен только запускающему проверку. B0/B1/B2 используют одинаковый вход; правила baseline остаются из документа 04.

Манифест: хеш исходного набора, отдельный хеш labels при наличии, версии схемы/алгоритма/справочника/адаптера, контрольное `as_of`, числа записей и длительность запуска. Даты и актуальность рассчитываются относительно `as_of`, не текущих часов; равные баллы упорядочиваются по `candidate_id`. При одинаковых входах и версиях выдача и метрики совпадают, кроме технических полей времени выполнения.

Проверить до расчёта: уникальность JSON-ключей и ID, конечные числовые значения и диапазоны, даты не позже `as_of` для подтверждений, зарплатные границы, допустимые enum/технологии/навыки, согласованность подтверждений и ссылок. Неизвестные поля отклоняются с путём до поля. Несовместимые условия — допустимый сценарий исключения, а не повреждённый файл. Пустые массивы допустимы и дают пустой отчёт с объяснением; отсутствие самих полей — ошибка. Ограничения MVP на файл: 10 MiB, до 1000 кандидатов, до 100 потребностей; labels — до 100000 уникальных пар и 10 MiB. Превышение явно отклоняется, данные не обрезаются.

При ошибке входа пакет не запускается частично: `errors.json` содержит запись/поле/причину, без копирования всего профиля. Exit code: 0 — успешно (включая неполную/отсутствующую разметку с соответствующим статусом); 2 — неверный вход или аргументы; 1 — технический сбой. Пустая папка результата создаётся до работы; существующие непустые папки не перезаписываются. Отчёт успеха публикуется только после завершения всех расчётов, при сбое не выдаётся частичный результат за полный. Повторный запуск в новой папке не создаёт пользователей или дублей в продукте.

### 11.6. Что именно проверяет этот режим

Режим проверяет допуск, релевантность выдачи и объяснения при заданных характеристиках кандидатов. Он не доказывает, что входные грейды определены верно, не проверяет самостоятельность прохождения и не заменяет пилот оценки. Произвольные резюме без структурированных признаков и неподдерживаемые категории получают понятную инструкцию о границах, а не фиктивную «успешную загрузку».
