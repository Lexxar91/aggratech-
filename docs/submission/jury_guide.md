Проверка навыков и поиск специалистов

Руководство для жюри · 11 октября 2026 года

## 01 / Что делает продукт

Aggratech помогает кандидату подтвердить навыки, а компании — найти специалиста с подходящим уровнем и условиями работы. Сейчас проверяется Backend на Python и SQL: Junior и Middle. Уровень определяется заданиями, а не длиной резюме, достижениями ФСП или выбранной вакансией.

Кандидат заполняет профиль, проходит проверку, выбирает результат для публикации и получает предложения. Работодатель описывает потребность, видит подборку с объяснениями, приглашает кандидатов и размещает вакансии. Контакты открываются конкретной компании по согласию кандидата.

### Что увидит эксперт после запуска

| В приложении | Наполнение |
|---|---|
| Кандидаты | 12 профилей Junior/Middle с разными условиями поиска |
| Компании | 3 работодателя с отдельными кабинетами |
| Работа | 9 вакансий: 6 опубликованных и 3 закрытых |
| Общение | 15 приглашений и 18 откликов в разных состояниях |
| Поиск | 3 сохранённые непустые подборки |

Биографии стартовых кандидатов вымышлены. Их уровни получены штатным выполнением решений и оцениванием v3, а не записью готовых баллов. Эти прохождения нужны для проверки продукта и не входят в статистику людей. Повторное заполнение не меняет пользовательские профили, пароли и согласия.

## 02 / Сборка и запуск

### Одна команда

Нужны Docker Engine с Linux-контейнерами и плагин Docker Compose. Для изоляции решений требуются cgroup v2 и стандартный seccomp. При первой сборке нужен интернет для загрузки образов и зависимостей. Python, Node.js, отдельная VM и GPU на компьютере эксперта не нужны.

Откройте терминал в корне полученного репозитория и выполните:

```bash
docker compose up --build -d --wait --wait-timeout 1800
```

Первый запуск собирает интерфейс, применяет миграции и выполняет решения стартовых кандидатов. Это может занять несколько минут. Параметр wait ждёт готовности сервисов; 1800 — предел ожидания команды, а не обещанное время запуска.

| Адрес | Назначение |
|---|---|
| http://localhost:18000 | Веб-приложение |
| http://localhost:18025 | Mailpit: письма подтверждения и уведомления |
| http://localhost:18000/docs | Интерактивное описание API |
| http://localhost:18000/openapi.json | Машиночитаемая схема API |

## 03 / Архитектура

### Одна система, отдельное исполнение решений

React-интерфейс собирается Vite внутри Docker и раздаётся FastAPI с того же адреса, что и API. Бизнес-правила находятся на сервере. PostgreSQL хранит профили, прохождения, результаты, потребности, приглашения, вакансии и согласия. Worker выполняет оценивание в фоне. Mailpit принимает почту на проверочном стенде.

[diagram:architecture]

### Почему решения изолированы

Python и SQL кандидата не исполняются в процессе API. Worker обращается по mTLS к runner-controller. Контроллер допускает только фиксированные образы и разрешённые параметры запуска. API не имеет доступа к Docker socket. PostgreSQL 17 продуктовой БД отделён от PostgreSQL 18, используемого для SQL-заданий.

Для контейнера решения отключена сеть, корневая файловая система доступна только для чтения. Временная область очищается после задания. Заданы ограничения CPU, памяти, процессов, времени и вывода; используется непривилегированный пользователь, drop ALL capabilities, no-new-privileges и seccomp. Privileged-режим запрещён. Секреты приложения, продуктовая БД, исходники проверяющего кода и host mounts в контейнер решения не передаются.

Это docker-limited: ограничения контейнера с общим ядром хоста. Они не эквивалентны VM или gVisor и не означают подтверждённую production-безопасность.

### Данные и доступ

Основные связи: пользователь → профиль → прохождение → доказательства навыков → опубликованный результат; работодатель → потребность → снимок подборки; приглашение или отклик → разрешение выбранных контактов.

Каждое действие проверяет роль и владельца объекта. Принятие приглашения и создание разрешения контактов происходят в одной транзакции. Отклик и его согласие также сохраняются атомарно. Удаление одного источника согласия не закрывает контакты, разрешённые другим действующим источником.

## 04 / Проверка навыков и подтверждение уровня

### Путь кандидата

Кандидат подтверждает email, заполняет профиль и выбирает уровень. Опрос подготавливает прохождение, но не присваивает Junior или Middle. Вариант заданий выбирает сервер по правилам банка и истории уже показанных задач.

[diagram:assessment]

В принятом банке v3 — 28 карточек: 14 для Junior и 14 для Middle. Один вариант содержит пять заданий в части A и два в части B. На A отведено 30 минут, на B — 15 минут. Начать B нужно в течение 24 часов после сдачи A; ждать сутки не требуется.

Задание проверяет основное решение и решение при изменённом условии. Кандидат может сохранять черновик. Отправка необратима и передаёт текущий введённый текст. Черновик v3 не становится отправленным решением автоматически при истечении таймера: незавершённость фиксируется отдельно.

### Что оценивается

Python проверяется исполнением в отдельном контейнере. SQL исполняется в изолированном PostgreSQL: сравниваются результат, состояние и требуемые действия. Запрос не обязан совпадать текстом с одной эталонной строкой. В обоих случаях учитываются предусмотренные заданием ограничения; закрытые тесты и правильные решения клиенту не передаются.

| Балл завершённого задания | Что означает |
|---|---|
| 0 | Не пройден ни один основной проверочный случай |
| 1 | Пройдена часть основных случаев |
| 2 | Основные случаи пройдены; обязательные границы или вторая часть не выполнены полностью |
| 3 | Основные требования и вторая часть выполнены; дополнительные требования качества выполнены не полностью |
| 4 | Выполнены все предусмотренные требования |

Синтаксическая ошибка в окончательно отправленном решении — ошибка решения. Отсутствие отправки, незавершённость, инфраструктурный сбой и необходимость проверки не превращаются в нулевой балл навыка.

### Почему высокий общий балл может не подтвердить уровень

Общий балл описывает профиль, но не компенсирует обязательные требования. Для SQL и HTTP/API нужны три независимых источника доказательств, включая вторую сессию; каждый результат не ниже 3 из 4. Для остальных областей нужны два независимых результата: оба не ниже 2, хотя бы один не ниже 3. Связанные задачи не считаются несколькими независимыми доказательствами только потому, что у них разный язык.

Наблюдаемое раскрытие или изменение чужих данных, повторное списание и запись неподписанного события блокируют подтверждение независимо от общего балла. Это функциональные нарушения, а не автоматическое обвинение в списывании. Кандидат видит понятную причину без скрытых тестов.

| Область | Вес Junior | Вес Middle |
|---|---|---|
| Python и алгоритмы | 20% | 10% |
| SQL и данные | 30% | 20% |
| HTTP и API | 20% | 20% |
| Отладка и надёжность | 20% | 30% |
| Безопасность и валидация | 10% | 20% |

### Результаты, история и повторные попытки

Система различает четыре результата: уровень подтверждён; требования пока не выполнены; недостаточно данных; требуется проверка достоверности. Технический сбой показывается как состояние процесса и не доказывает недостаток навыка.

После успеха кандидат выбирает публикацию результата. Работодатель видит только разрешённую сводку навыков, дату и основания. Неуспешная новая попытка не понижает опубликованный уровень автоматически. История сохраняется; нельзя просто выбрать максимальный балл из всех попыток.

Повтор одного уровня доступен не ранее семи суток; ограничение — два завершённых цикла за 30 суток. Показанные задачи учитываются и при смене уровня. При исчерпании доступных вариантов повтор не создаёт новые доказательства. Переход Junior → Middle требует отдельного прохождения; отказ Middle не присваивает Junior автоматически. Апелляция сохраняет обращение, решение и аудит, а не переписывает баллы без основания.

Банк и методика v3 проверены людьми и приняты пользователем 11.10.2026. Допуск исполнения проверяется по актуальным хешам материалов, источника и оценщика; изменение оценщика требует нового технического прогона. Это не подменяется ручной записью успешного статуса. Из принятия материалов не выводятся отсутствующие численные показатели статистической точности.

## 05 / Подбор, категории и объяснения

### Сначала совместимость, затем порядок

Категория — специализация и подтверждённый уровень. Достижения ФСП не присваивают грейд. Компания задаёт потребность сама или редактирует один из трёх шаблонов. Фильтры проверяют публикацию и видимость профиля, категорию, обязательные подтверждённые навыки, условия работы и зарплатную совместимость.

Известная несовместимость исключает кандидата. Неизвестные условия показываются отдельной группой «Нужно уточнить»; они не выдаются за выполненное требование. Неподтверждённый уровень не проходит в подтверждённую подборку через эту группу.

### Формула внутри одной категории и группы

```text
Score = clamp(55*T + 25*K + 8*A + 7*F + 5*U - P, 0, 100)
```

| Компонент | Смысл и правило |
|---|---|
| T — навыки | Средняя нормированная оценка нужных навыков; высокий приоритет весит 2, обычный — 1 |
| K — технологии | Подтверждённая технология: 1; указанная без проверки: 0,6; отсутствующая: 0. Обязательная весит 2, желательная — 1 |
| A — выход на работу | Вовремя: 1; опоздание d дней: max(0, 1 − d/30); дата неизвестна: 0 и группа уточнения |
| F — ФСП | 1 при подтверждённом происхождении и принадлежности достижения, иначе 0 |
| U — свежесть навыков | До 90 дней: 1; 91–180: 0,5; старше или без доказательств: 0 |
| P — условия поиска | Последнее явное подтверждение до 90 дней: 0; 91–180: 3; старше или неизвестно: 5 |

Если срок выхода не важен, A = 1 для всех; если стек не задан, K = 1. Без истории ФСП F = 0, остальные веса сохраняются. Более низкая зарплата, длинное резюме и фотография не дают бонусов. Указанная технология не становится подтверждённой только из-за решения на другом языке.

При равенстве используется порядок Score → T → K → стабильный candidate_id. Приоритет SQL или HTTP меняет порядок через T и отображается в объяснении. Балл подбора — не вероятность найма.

Система сохраняет снимок потребности и выдачи с временем расчёта. Компания может сохранить или скрыть кандидата для этой потребности. Сравнение разрешено для двух доступных карточек одной категории, группы и версии подборки. Старый снимок не отменяет текущую приватность: при открытии карточки, сравнении и PDF права проверяются заново.

## 06 / Предложения, вакансии и контакты

### Предложение конкретному кандидату

Приглашение не требует вакансии. Работодатель указывает зарплатный диапазон в рублях за месяц до налогов, условия и свой контакт. Снимок предложения неизменяем; последующее редактирование потребности его не переписывает. Для изменения предложения его нужно отозвать и отправить заново.

Шесть статусов: отправлено, просмотрено, принято, отклонено, отозвано, истекло. Срок действия — семь суток. Идемпотентный повтор не создаёт дубликат; действующее приглашение ограничивает повтор по той же потребности и кандидату. Уведомления сообщают статус и ссылку без контактов кандидата.

### Вакансия и самостоятельный отклик

Компания создаёт, редактирует и закрывает вакансию. Для публикации обязателен зарплатный диапазон в рублях. Закрытая вакансия сохраняет историю, но не принимает новые отклики. Кандидат может откликнуться без подтверждённого грейда: это не создаёт квалификацию и не обходит правила подборки.

При отклике фиксируются условия вакансии и выбранные контакты. Повторная подача возвращает прежний отклик. Статусы: отправлен, просмотрен, принят, отклонён, отозван. Редактирование вакансии не меняет снимок уже отправленного отклика.

### Кто получает контакты

До согласия контакты закрыты в карточке, API, PDF и уведомлениях. Принятие приглашения или отправка отклика создаёт разрешение только соответствующей компании и только на выбранные поля: email, телефон, мессенджеры.

Отзыв отклика закрывает его источник разрешения. Другой действующий отклик или приглашение продолжает разрешать свои поля. Общий отзыв согласия или блокировка работодателя закрывает соответствующие разрешения полностью. Новые ответы и новые PDF учитывают отзыв; уже скачанный файл невозможно отозвать удалённо.

## 07 / Интеграция с ФСП и FSP ID

### Что реализовано сейчас

Используется тестовый каталог ФСП, без обращения к боевому реестру. Привязка проверяет принадлежность учётной записи: одного чужого ID недостаточно. Повторная синхронизация не дублирует события; отзыв связи удаляет привязку и кэш. Источник событий сохраняется явно.

Тестовые события не выдаются за настоящие достижения: в продуктовой формуле они не дают подтверждённый бонус ФСП. В автономном наборе можно задать синтетическое подтверждение, чтобы проверить вклад компонента F. Стартовые продуктовые профили без ФСП остаются доступными для подбора.

[diagram:fsp]

### Предполагаемая схема FSP ID

После получения доступа: браузер переходит к FSP ID → сервер принимает callback → проверяет state, nonce, подпись и claims → связывает subject с локальным пользователем → отдельный серверный адаптер запрашивает достижения. Предполагаемый протокол — OpenID Connect; окончательные адреса, scope, договор передачи данных и правила доверия согласуются с ФСП.

Данные реестра должны сохранять источник, идентификатор события, владельца и дату проверки. Ошибка внешнего сервиса не должна блокировать локальный вход или превращать отсутствие ответа в отсутствие достижения. Токены остаются на сервере. Это схема предполагаемой интеграции, а не заявление о работающем SSO или Keycloak. Боевые ключи, реальный реестр и реальный FSP ID в поставку не входят.

## 08 / Валидация: процедура и фактические результаты

### Как разделяются доказательства

Протокол проверки — docs/04_validation_procedure.md. Техническая проверка исполнения, принятие содержимого людьми, статистическая оценка методики и разметка подбора — разные источники. Успешные автоматические тесты не заменяют исследования на людях.

Для банка проверяются правильные и ошибочные решения, частичные ответы, вторая часть без адаптации, альтернативный SQL, технические отказы и соответствие хешей. Для продукта — обе роли, принадлежность объектов, приватность, конкурентные операции PostgreSQL и сквозные браузерные сценарии.

### Контроль подбора

Набор содержит 120 искусственных кандидатов, 12 потребностей и 6 работодателей. Разделение зафиксировано: 40/80 кандидатов, 4/8 потребностей. На контрольных 80 кандидатах и восьми потребностях рассчитаны B0, B1 и B2 при одинаковых входах и фиксированном as_of = 2026-10-09T12:00:00Z.

B0 — фильтры и стабильный порядок; B1 — фильтры и стек; B2 — полная формула. Labels передаются оценщику метрик после ранжирования. Изменение labels не меняет баллы и порядок; при неполной разметке для потребности указывается «не измерено». Веса по контрольному набору не подбирались.

| Среднее по 8 контрольным потребностям, основная группа | Precision@10 | Recall@20 | nDCG@10 |
|---|---|---|---|
| B0 | 0,412500 | 1,000000 | 0,551119 |
| B1 | 0,437500 | 1,000000 | 0,514115 |
| B2 | 0,462500 | 1,000000 | 0,563565 |

Это арифметическое среднее значений из сохранённого metrics.json. Разметка синтетическая: цифры проверяют работу вычислений, а не качество найма. В некоторых потребностях B2 хуже B0; улучшение в среднем не является доказательством универсального преимущества. Recall@20 = 1 на этом небольшом наборе не означает идеальную полноту для рынка.

Отдельно зафиксированы 558 независимых сверок вычислений и эксперименты с вкладом ФСП, актуальности и доступности. Исходные отчёты: docs/release/technical/report.md и docs/release/technical/v3-cli/. Для человеческой разметки протокол требует двух разметчиков до просмотра ранжирования; непредоставленные численные результаты такой разметки здесь не заявляются.

### Что известно о человеческой проверке

Протокол оценки заданий предусматривает фиксацию исходного опыта участника до просмотра результата, времени выполнения, затруднений и причин итогового решения. Сопоставимость проверяют на разных вариантах и уровнях, сохраняя исходные наблюдения и разногласия проверяющих; оценку понятности интерфейса отделяют от правильности решения. Пороговые правила фиксируются до контрольных прохождений. Отчёт должен указывать состав участников и источник каждой оценки; технические аккаунты исключаются.

Банк и методика v3 проверены людьми и приняты пользователем. Этот факт сохраняется. Численные показатели точности уровня, сопоставимости вариантов и грейдов, качества подбора для реальных работодателей в предоставленных текущих отчётах не измерены. Стартовые и технические прогоны не используются для заполнения этих пробелов.

## 09 / Автономная проверка жюри

CLI использует общий с API алгоритм. Ему не нужны БД, почта, runner, пользовательский аккаунт или внешние ключи. Он читает dataset и необязательные labels из JSON, валидирует вход и создаёт четыре файла: rankings.json, metrics.json, report.md, run_manifest.json.

После обычной сборки образ aggratech:app уже доступен. Из корня проекта:

```bash
mkdir -p artifacts/jury-example artifacts/jury-run
docker run --rm --network none \
  --user "$(id -u):$(id -g)" \
  -v "$PWD/artifacts/jury-example:/output" \
  aggratech:app python -m app.tools.matching_check \
  --write-example /output
```

```bash
docker run --rm --network none \
  -v "$PWD/artifacts/jury-example:/input:ro" \
  aggratech:app python -m app.tools.matching_check \
  --input /input/dataset.json --validate-only
```

```bash
docker run --rm --network none \
  --user "$(id -u):$(id -g)" \
  -v "$PWD/artifacts/jury-example:/input:ro" \
  -v "$PWD/artifacts/jury-run:/output" \
  aggratech:app python -m app.tools.matching_check \
  --input /input/dataset.json --labels /input/labels.json \
  --output /output
```

Каталоги вывода должны быть новыми или пустыми: CLI не перезаписывает существующий отчёт. Пример создаёт схемы, словарь и dataset с фиксированным as_of. Чтобы проверить неполную разметку, запускайте без labels или с явно частичной разметкой; пропуски не становятся отрицательными ответами.

Лимиты: 10 MiB на файл, 1000 кандидатов, 100 потребностей, 100 000 пар. Ошибки формата дают код выхода 2 и путь поля; технический сбой — 1; успешный расчёт, в том числе без labels, — 0. Поддельные продуктовые подтверждения из CLI в БД не записываются. Схемы и словарь: docs/release/cli-input/.

## 10 / Сценарий знакомства с продуктом

### Быстрый обход готовых кабинетов

1. Войдите employer01. Откройте потребность и подборку, измените приоритет навыка и сравните две доступные карточки. Проверьте объяснения, неизвестные условия и отсутствие контактов до согласия.
2. Создайте приглашение с зарплатой. В отдельном браузере войдите соответствующим кандидатом, откройте предложение и разрешите только email. Вернитесь к работодателю: телефон должен остаться закрытым.
3. Скачайте PDF, отзовите разрешение кандидатом и скачайте новый PDF. Новая версия должна учитывать отзыв; ранее сохранённый файл остаётся у получателя.
4. Откройте опубликованную вакансию, отправьте отклик с выбранными контактами, проверьте его в кабинете компании. Отзовите отклик: разрешение от другого действующего предложения должно сохраниться.
5. Откройте закрытую вакансию: новый отклик недоступен. Проверьте профиль candidate12: он не входит в поиск.

### Полная проверка нового уровня

Зарегистрируйте нового кандидата, подтвердите адрес через Mailpit и заполните профиль. Выберите Junior или Middle, решите Python/SQL-задания обеих частей. Проверьте сохранение черновика после обновления страницы и окончательную отправку текущего кода. После оценивания откройте причины результата. При успехе опубликуйте его и проверьте появление в подходящей потребности работодателя.

Лимит работы над заданиями — до 45 минут суммарно; пауза между A и B не входит в это время. Готовые аккаунты уже проходили проверку, поэтому на них действуют ограничения повторных попыток.

## 11 / Границы решения и состав сдачи

Реализованы кабинеты двух ролей, проверка Backend Junior/Middle, поиск по навыкам и условиям, объяснения, приглашения, вакансии, отклики, контактные согласия и PDF. ФСП подключён через тестовый адаптер. Реального FSP ID, ATS, парсинга резюме, регулярных заданий и проверки Senior в поставке нет. В пользовательском процессе не используются LLM, внешние модели или платные API; GPU не требуется.

Версии библиотек и все 83 операции на 70 путях API приведены в отдельном PDF. Первичные машиночитаемые источники — docs/release/openapi.json, pyproject.toml, uv.lock, frontend/package.json и frontend/package-lock.json.

Ссылка на репозиторий: https://github.com/Lexxar91/aggratech-. По Q&A §7 перед сдачей нужно обеспечить экспертам просмотр и прикрепить ссылку внутри выбранной задачи. Доступ без учётной записи команды и фактическое прикрепление ссылки в рамках подготовки документов не проверялись и не выполнялись.

Закрытые ответы, эталоны, скрытые тесты, .env, ключи, токены и персональные реестры не входят в публичные PDF. Исходники, необходимые для сборки, передаются экспертам с согласованным доступом; публичная раздача секретов или закрытого банка не требуется для чтения этого комплекта.

PDF-руководство не объявляет приложение production-ready. Оно описывает реализованный продукт, зафиксированные проверки и пределы доступных доказательств.
