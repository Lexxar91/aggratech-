# Порядок реализации обязательного MVP

## Основание и границы

Прочитаны docs/00–06. Объём и приоритеты определяет **06_plan.md с дополнениями от 07.10.2026 и изменением изоляции от 09.10.2026**; правила assessment — 02, matching — 03, валидации — 04, архитектуры — 05.

Существенных неразрешённых противоречий нет. Устаревшие упоминания четырёх категорий в 03 и «будущего веб-клиента» в 05 не расширяют и не сокращают актуальный релиз: **Backend Junior/Middle и работающий интерфейс обеих ролей**.

Порядок ниже задаёт законченные этапы, а не отдельные функции. Подготовка материалов начинается заранее; пользовательские экраны реализуются вместе с соответствующим поведением.

## Статусы этапов

- `не начат` — реализация этапа ещё не началась.
- `в работе` — этап реализуется или проходит проверки.
- `завершён` — выполнен Definition of Done и пройдены обязательные проверки этапа.

## Этапы реализации

### 1. Воспроизводимое окружение, изоляция и подготовка доказательств

**Статус:** завершён

**Текущее состояние 09.10.2026:** docker-limited реализован, ограничения
фактически проверены. Пользователь подтвердил самостоятельный запуск Compose,
Docker-проверки и отчёт банка v1: passed, 154 проверки, technical_errors пуст.
Замечания X1/X4 Junior исправлены в v2; повторный прогон passed, 160 проверок, technical_errors пуст.
Проверка объективности оценки и сложности перенесена в финальный этап 9.

**Согласованное изменение 09.10.2026:** docker-limited через Docker Compose без отдельной runner VM. Только отдельный контроллер получает Docker socket и запускает фиксированный образ с параметрами из allowlist; API socket не получает. Это ограниченная контейнерная изоляция для демо, не эквивалент gVisor/VM и не заявление о production-безопасности. Фактическая проверка ограничений обязательна. Самостоятельный запуск и Docker-проверки подтверждены пользователем 09.10.2026. VM-блокер снят выбранным docker-limited; прежние записи сохранены как история.

**Проверяемый результат:** приложение запускается по инструкции, сохраняемая очередь обрабатывает задания, Python-код исполняется в отдельном одноразовом контейнере docker-limited. Жюри запускает приложение и runner обычным Docker Compose без установки VM.

**Зависимости:** отсутствуют.

**Входит:**

- Каркас модульного монолита, API и одного worker, PostgreSQL, Alembic, Docker Compose, Mailpit.
- Каркас веб-клиента HTML/CSS/JavaScript под одним origin.
- Очередь с атомарным захватом, ограниченными повторами, восстановлением и идемпотентной обработкой.
- Runner Python 3.14 с фиксированным образом, защищённым соединением и ограничениями из 05.
- Healthcheck, безопасные логи, идентификаторы запросов и заданий.
- Матрица X/Y; первые два полностью подготовленных семейства, включая X4; минимальный запуск `bank_quality`.
- Паспорта экспериментов, разделение разработочных, контрольных и демонстрационных данных; три исходных описания вакансий.
- Подготовка протокола добровольцев и расписания. Приглашения людям отправляет команда.

**Не входит:** пользовательский assessment, полный банк, подбор, дополнительные инфраструктурные сервисы.

**Definition of Done:**

- Другой участник воспроизводит запуск и применение миграции к пустой БД.
- Контейнер задачи не получает сеть, секреты приложения, доступ к БД, исходникам оценщика и host mounts. Фактически проверены read-only root, очищаемый tmpfs, CPU/RAM/процессы/время/вывод, непривилегированный пользователь, drop ALL, no-new-privileges и seccomp; privileged запрещён. API не получает Docker socket, управление контроллером ограничено фиксированным образом и параметрами allowlist.
- Остановка worker не теряет задание и не создаёт повторный бизнес-результат.
- Зафиксированы стоимость первых материалов и оценка затрат на JSON CLI; бюджет пересчитан без скрытого сокращения P0.

**Пакет проверок:** сборка образов и запуск; миграция; live/ready; захват и восстановление очереди; ограничения CPU/памяти/процессов/вывода, очистка среды и запреты доступа runner; техническая проверка первых двух семейств.

### 2. Учётные записи, профили и базовая приватность

**Статус:** завершён

**Проверяемый результат:** кандидат и работодатель регистрируются через браузер, подтверждают email и сохраняют свои профили; кандидат получает PDF.

**Зависимости:** этап 1.

**Входит:**

- Auth и управление сессиями по 05, подтверждение email и восстановление пароля.
- Два ролевых кабинета, ручной ввод профиля, контакты, предпочтения, согласия и блокировки работодателей.
- Раздельные модели безопасной карточки и контактов.
- PDF с кириллицей и проверкой текущих прав.
- Справочники и базовые контракты API.

**Не входит:** присвоение категории, раскрытие контактов через приглашение, распознавание резюме, OIDC.

**Definition of Done:**

- Основные действия доступны в интерфейсе и сохраняются после перезапуска.
- Подмена идентификаторов не открывает чужие данные.
- Неподтверждённый email не допускается к зачётной оценке.
- PDF и API соблюдают одинаковые ограничения видимости.

**Пакет проверок:** интеграционные тесты регистрации, токенов, refresh-ротации, выхода и восстановления пароля; матрица ролей и владельцев; CSRF для cookie-операций; проверки PDF; браузерный сценарий регистрации и профиля.

### 3. Полный банк и автоматический допуск

**Статус:** техническая часть завершена и принята. По решению пользователя независимое review банка, проверки человеком и зачётный допуск перенесены в этап 9. `admission_status=not_admitted` сохраняется; банк доступен только для явно демонстрационных/тестовых прохождений.

**Проверяемый результат:** обе формы X/Y допущены для Junior и Middle на основании воспроизводимого технического отчёта.

**Зависимости:** этап 1; подготовка может идти одновременно с этапом 2.

**Входит:**

- 12 семейств, 24 версии уровня, две формы по 4 A + 2 B.
- Условия, перенос, рубрики, эталоны, допустимые альтернативы, типичные ошибки и минимум три набора параметров на грейд.
- Python и структурированные ответы; SQL без сравнения только с одной эталонной строкой.
- `BankQualityChecker`, версионирование и допуск по хешам материалов и версии оценщика.
- `CandidateTestEvaluator` для X4/Y4: 2–3 случая, две корректные и три ошибочные реализации на грейд.
- Три таблицы «требование вакансии → навык → семейство → действие → рубрика».

**Не входит:** дополнительные семейства, редактор банка, новые runtime, генератор мутаций, доказательство сопоставимой сложности на людях.

**Definition of Done:**

- Обе формы выполняют требования покрытия из 02 и не пересекаются.
- Каждый комплект материалов прошёл взаимную проверку и автоматический допуск.
- Ошибочная, изменённая или технически непроверенная версия не допускается.
- X4/Y4 учитываются внутри существующей рубрики без дополнительных баллов и независимых доказательств.
- Закрытые материалы отсутствуют в публичной сводке.

**Пакет проверок:** полный прогон `bank_quality` для 24 версий; эталоны и альтернативы; частичные и ошибочные ответы; перенос без адаптации; покрытие; негативные проверки допуска; все четыре комплекта X4/Y4 по 04 §2.8.

### 4. Полный assessment, публикация категории и переход грейда

**Статус:** технический демонстрационный путь реализован и проверен. Зачётная приёмка заблокирована до независимого review и допуска банка на этапе 9; `admission_status=not_admitted`. Ограничение автоматической проверки качества X1 Middle записано в журнале ниже.

**Проверяемый результат:** кандидат проходит A/B, получает обоснованный результат и выбирает публикацию либо допустимый переход на соседний уровень.

**Зависимости:** этапы 2 и 3.

**Входит:**

- Опрос, выбор предполагаемого грейда, создание цикла, выдача текущего этапа, черновики и окончательная фиксация ответов.
- A до 30 минут; B до 15 минут, доступная сразу после сдачи A независимо от завершения фоновой проверки.
- Срок начала B — 24 часа; восстановление и служебное продление при техническом сбое.
- Оценивание, достаточность доказательств, история, публикация категории и безопасные основания в карточке/PDF.
- Переходы Junior↔Middle, лимиты 7/30 дней, общий учёт показанных семейств и исчерпание банка.
- Минимальная служебная обработка апелляций с аудитом, без отдельного кабинета.
- Реальное исполнение демонстрационного цикла; прохождения человеком по протоколу 04 перенесены в этап 9 по решению пользователя.

**Не входит:** автоматическое понижение, третий цикл на знакомых семействах, AI-режим, расширенный антифрод и новые категории.

**Definition of Done:**

- Все четыре результата из 02 различаются: подтверждён, не подтверждён, недостаточно данных, требуется проверка.
- Высокая сумма не компенсирует провал критического навыка.
- До публикации категория недоступна подтверждённому подбору.
- Оба направления перехода проходят на другой форме; неуспешный переход сохраняет прежнее успешное подтверждение.
- Ошибка инфраструктуры не становится ошибкой кандидата.
- Есть реальное завершённое прохождение для демонстрации, отдельно от seed-истории.

**Пакет проверок:** рубрики и независимость доказательств; границы 30/15 минут, 24 часов, 7/30 суток с управляемым временем; оба перехода; публикация сохранённого результата; исчерпание банка; конкурентное создание цикла; повторная доставка; восстановление; защита закрытых этапов; браузерный цикл A/B.

### 5. Объяснимый matching, ФСП mock и автономная проверка жюри

**Статус:** техническая часть реализована и проверена на явно синтетических данных. Полная приёмка не завершена: подбор и сравнение реальных опубликованных зачётных профилей заблокированы независимым review/допуском банка на этапе 9. `admission_status=not_admitted` сохранён. Демо и fixture в подтверждённый подбор не включаются.

**Проверяемый результат:** работодатель получает воспроизводимую подборку из реальных опубликованных результатов; тот же алгоритм работает через JSON CLI без инфраструктуры приложения.

**Зависимости:** этапы 2 и 4 для продуктовой приёмки. Схемы JSON и разработочные примеры готовятся с этапа 1.

**Входит:**

- EmployerNeed, три редактируемых шаблона, фильтры и отдельная группа уточнения.
- Формула из 03 без изменения весов, стабильный порядок, объяснения и снимки версий.
- Сохранение и скрытие кандидатов в рамках потребности.
- Сравнение двух доступных карточек одной категории, группы и версии подборки.
- Привязка ФСП через mock с проверкой принадлежности и явным происхождением данных.
- Общие DTO и вычислительный код для продуктового пути и `app.tools.matching_check`.
- Схемы dataset/labels, словарь, пример, `--write-example`, `--validate-only`, запуск B0/B1/B2 и отчёты по 03 §11.

**Не входит:** новый алгоритм, публичный импорт, загрузка резюме, настоящий реестр ФСП, подтверждение fixture-грейдов сервисом.

**Definition of Done:**

- SQL/HTTP-приоритет меняет порядок подготовленных кандидатов и объяснение.
- Без ФСП используется `F = 0`, остальные веса сохраняются.
- Старые подборки и сравнение повторно проверяют приватность.
- CLI использует общий matching, фиксированное `as_of` и не подключается к БД, почте или runner.
- Labels доступны только оценщику метрик после построения выдачи.
- Поставляются четыре выходных артефакта и документированные ошибки из 03.

**Пакет проверок:** фильтры, компоненты формулы и равные баллы; зарплатные границы и неизвестные условия; шаблоны и сравнение; отсутствие/дубли ФСП; актуальная приватность; весь пакет 04 §3.4.2, включая новый набор, совпадение API/CLI, замену labels, неполную разметку, лимиты и отсутствие продуктовых записей.

### 6. Приглашение, согласие и доступ к контактам

**Статус:** технически завершён в согласованном тестовом режиме. Приёмка на реальных подтверждённых профилях и независимая проверка человеком ожидают этапа 9; `admission_status=not_admitted` сохранён.

**Проверяемый результат:** работодатель приглашает кандидата без вакансии; кандидат видит зарплату и принимает предложение; разрешённые контакты открываются только отправителю.

**Зависимости:** этап 5.

**Входит:**

- Неизменяемый снимок предложения, обязательная зарплата, повторная проверка условий.
- Все шесть статусов, уведомления и срок действия семь суток.
- Идемпотентность и ограничение активных приглашений.
- Атомарное принятие с созданием `ContactGrant`.
- Отзыв разрешения и закрытие всех контактов конкретному работодателю.

**Не входит:** вакансии и самостоятельные отклики — следующий отдельный этап после проверки доказательств.

**Definition of Done:**

- Полная основная цепочка проходит через браузер.
- До согласия контакты отсутствуют во всех представлениях и уведомлениях.
- Конкурирующие принятие, отзыв и истечение дают один допустимый итог.
- Другой работодатель не получает разрешение отправителя.

**Пакет проверок:** таблица переходов; повторные запросы; гонки на PostgreSQL; истечение на границе срока; зарплата; изменение потребности после отправки; матрица доступа к карточкам, контактам и PDF; отзыв согласия.

### 7. Контрольные измерения и отчёт основных механик

**Статус:** техническая часть выполнена на явно синтетических данных; полная приёмка не закрыта. Независимая человеческая разметка/review, реальные прохождения и проверка понятности отложены до этапа 9. Банк остаётся `not_admitted`; реальные подтверждённые результаты не заменены fixtures.

**Проверяемый результат:** имеются фактические, воспроизводимые доказательства работы assessment и matching с явно указанными ограничениями.

**Зависимости:** этапы 3–6. Подготовка данных начинается на этапе 1; по решению пользователя все человеческие прохождения перенесены в этап 9.

**Входит:**

- Набор 120 кандидатов, 12 потребностей и 6 работодателей; разделение 40/80 кандидатов и 4/8 потребностей.
- Подготовка процедуры разметки двумя участниками команды с сохранением разногласий; человеческая разметка и её review отложены до этапа 9.
- Контрольное сравнение B0/B1/B2, результаты всех восьми потребностей и отдельная проверка вклада ФСП, актуальности и доступности.
- Подготовка малого пилота: цель — четыре внешних добровольца, два цикла одного грейда на человека; человеческие прохождения выполняются на этапе 9.
- Подготовка проверки понятности шаблонов, объяснений и сравнения карточек; проверка с людьми — на этапе 9.
- Служебная сводка заданий по 04 §5.4 из реальных сохранённых прохождений.
- Фактические измерения времени и безопасные материалы для жюри.

**Не входит:** настройка весов по контрольным результатам, большой пилот, независимая экспертная сертификация, массовые человеческие атаки.

**Definition of Done:**

- Отчёт содержит версии, исходные данные, знаменатели, ошибки и ограничения.
- При неполной разметке соответствующие метрики обозначены «не измерено».
- Переход между грейдами не выдан за повторяемость.
- Seed, fixture и технические прогоны не попадают в статистику людей.
- При недоборе добровольцев указаны фактическое число и незавершённая проверка; наблюдения не заменены синтетикой.
- Изменение правил после контроля отражается как новая версия, требующая нового контроля.

**Пакет проверок:** сверка метрик с независимыми контрольными расчётами; воспроизводимость отчётов; сверка сводки с попытками; проверка объяснений; проверка отсутствия закрытых материалов и персональных данных в публичных артефактах.

### 8. Вакансии и самостоятельные отклики

**Статус:** технически завершён; Definition of Done проверен автоматически
на явно тестовых профилях. Человеческая приёмка отложена до этапа 9.

**Проверяемый результат:** работодатель публикует вакансию с зарплатой, кандидат откликается с явным согласием, обе стороны видят статусы.

**Зависимости:** этапы 6 и 7. Этап остаётся обязательным даже при отсутствии добровольцев, если незавершённая проверка честно зафиксирована.

**Входит:**

- Создание, редактирование, просмотр и закрытие вакансий.
- Отклики, история и статусы из 05.
- Снимок условий вакансии на момент отклика.
- Атомарное создание отклика и разрешения на выбранные контакты.
- Отзыв отклика с отзывом только связанного с ним разрешения.

**Не входит:** парсинг вакансий, ATS, модераторский кабинет, регулярные задания.

**Definition of Done:**

- Вакансия без зарплаты не публикуется.
- Отклик доступен через интерфейс и не дублируется.
- Контакты открываются при согласованной подаче отклика.
- Отзыв одного источника не отменяет другое действующее согласие.

### Реализация

- `invitations`: обязательная зарплата RUB/месяц gross, описание, формат,
  существенные условия и контакт представителя; вакансия не требуется.
  Сохраняется неизменяемый снимок предложения, компании и версии потребности.
  Перед отправкой общая логика matching повторно проверяет текущую категорию,
  видимость, блокировку и известные условия с учётом конкретного предложения.
  Неизвестные условия обозначаются как требующие уточнения.
- Шесть состояний `sent/viewed/accepted/rejected/expired/withdrawn`;
  `viewed` только при авторизованном открытии кандидатом. Семь суток считаются
  от отправки; принятие на самой границе срока уже недоступно. Worker завершает
  просроченные предложения тем же кодом переходов.
- Идемпотентность отправки по ключу и хешу запроса; повтор с другим содержимым
  отклоняется. Ограничение — одно `sent/viewed/accepted` на пару
  «работодатель — потребность — кандидат». Есть лимит отправки по аккаунту/IP.
  Статусы, зарплата, срок, владелец, неизменяемость и активная пара закреплены
  миграцией `0005_invitations`, ограничениями и триггерами PostgreSQL.
- Принятие под блокировками профиля и приглашения атомарно создаёт один
  `ContactGrant` с выбранными полями, `contacts-v1`, источником и временем.
  Повтор принятия не расширяет и не восстанавливает отозванное разрешение.
  Контакты выдаются отдельным DTO только отправителю; карточки и снимки их
  не копируют. PDF включает только разрешённые поля при новом чтении.
- Отзыв всех разрешений компании сохраняет историческое `accepted`.
  Отзыв общего согласия и блокировка также закрывают разрешения; снятие блока
  или новое общее согласие старые разрешения не восстанавливают. Блокировка
  отзывает незавершённые приглашения. Неактивная компания не получает карточку,
  контакты или PDF. Скрытие из поиска прекращает новые приглашения, но сохраняет
  возможность ответить на ранее полученное предложение незаблокированной компании.
- Уведомления через транзакционную очередь и SMTP содержат статус/ссылку,
  без копии контактов кандидата. Добавлены экраны предложения, истории,
  просмотра, принятия/отказа, отзыва предложения и закрытия контактов.
  Аудит фиксирует исполнителей переходов, выдачи и отзыва согласия.

**Результат:** реализован и технически проверен только этап 8. Этап 9 не начат.

Реализованы `Vacancy`, `Application`, миграция `0006_vacancies`, API и браузерные

Публикация требует положительный упорядоченный диапазон RUB/gross и условия;
редактирование проверяет владельца и версию. Статусы отклика:
`submitted`, `viewed`, `accepted`, `rejected`, `withdrawn`.

Отклик, неизменяемый снимок условий и разрешение на явно выбранные контакты
создаются в одной транзакции PostgreSQL. Уникальность пары «вакансия — кандидат»
и блокировки защищают от повторной подачи и конкурентных изменений.
Повтор возвращает исходный отклик, включая отозванный и отклик закрытой вакансии,
без изменения согласия; новые отклики на закрытую вакансию отклоняются.
Снимок, принадлежность, версии и переходы дополнительно защищены ограничениями
и триггерами БД. Закрытие вакансии и отказ работодателя не отзывают согласие.

`ContactGrant` имеет ровно один источник: приглашение или отклик. Отзыв отклика
закрывает только его разрешение; остальные источники продолжают разрешать
свои поля. Общий отзыв согласия и блокировка работодателя закрывают все
соответствующие источники. API карточек, контактов, истории и новых PDF повторно
проверяют текущую приватность. Подтверждённый email необходим для подачи;
квалификация не обязательна для самостоятельного отклика.

обязательна, отклик подаётся через интерфейс без дубликатов, выбранные контакты
открываются при согласованной подаче, отзыв одного источника сохраняет остальные.
