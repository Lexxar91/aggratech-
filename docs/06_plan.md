

## Оптимизация объёма

Основание: [mvp_scope.md](../mvp_scope.md). Подтверждение грейда ограничено backend; frontend — справочники, blueprint и демонстрационная JS-задача без DOM/browser runtime и выдачи категории. Веб-интерфейс кандидата и работодателя остаётся обязательным.

Runner исполняет только Node.js JavaScript. На выделенной VM предпочтителен gVisor; резерв — restricted Docker для закрытого демо с ограничениями из `05_architecture.md`. SQL и диагностика проверяются структурированными ответами без отдельного SQL runtime. Очередь: таблица, один worker, статусы, ограниченные retries, восстановление и защита от повторного результата; сложная оркестрация не нужна.

Допустимы предзаполненные завершённые циклы для показа с явной маркировкой seed-истории. Они не являются реальными прохождениями и не доказывают качество грейдов. Вакансии, отклики, зарплата и приватность не сокращаются: `mvp_scope.md` этого не предлагает.

# План разработки MVP за 6 дней

Ниже — содержание четырёх документов. Основание: документы `00–04` и архитектура в `docs/05_architecture.md`.

Зафиксированные условия: **две подтверждаемые категории — Backend Junior/Middle; задания и данные готовит команда; отдельных экспертов нет**. Изолированный runner, вакансии и самостоятельные отклики сохраняются в объёме релиза.

**Это напряжённый план с высоким риском по срокам.** Главные ограничения — подготовка качественного банка заданий и проверка механики оценки. Полноценную независимую валидацию грейдов за шесть дней при этих ресурсах обещать нельзя.

В режиме планирования файлы не записываются.

## `docs/20_implementation_plan.md`

### Цель релиза

Подготовить запускаемый прототип, который демонстрирует полный путь:

**Регистрация → подтверждение email → профиль и опрос → выбор грейда → оценка A/B → категория → потребность работодателя → объяснимая подборка → приглашение с зарплатой → принятие → раскрытие контактов.**

Дополнительно показать работу без ФСП, публикацию вакансии и самостоятельный отклик.

Главные критерии оценки — подбор **35%** и тестирование с валидацией **25%**. Приоритет этих механик не отменяет обязательных требований к приватности, интерфейсу, документации и запуску.

### Организация команды

| Участник | Основная ответственность | Дополнительная ответственность |
|---|---|---|
| Разработчик A | Auth, профили, приватность, frontend, приглашения, вакансии и отклики | Интеграционные проверки доступа, документация запуска |
| Разработчик B | Assessment, runner, категоризация, EmployerNeed, matching, FSP mock | Банк заданий, проверка рубрик и правил грейда |

Банк заданий не оставлять одному разработчику B: каждый участник готовит часть материалов, другой проверяет. Такая проверка снижает ошибки, но **не заменяет независимую экспертную калибровку**.

Планировать около шести часов сосредоточенной работы на человека в день: всего **72 человеко-часа**, из них около **14 часов — резерв** на интеграцию и исправления. Это ограничение ёмкости команды, а не оценка, доказывающая достаточность времени.

### Приоритеты

У задач P0 отдельно отмечать основание:

- **ТЗ** — обязательное требование задания.
- **Проект** — принятое решение о составе текущего релиза.

| Приоритет | Содержание |
|---|---|
| **P0 — обязательное для сдачи** | Воспроизводимый запуск, два кабинета, email confirmation, профили и PDF, опрос, тестирование, категория, история и правила смены грейда, потребность, подбор и объяснения, приглашения с зарплатой, статусы, приватность, сценарий без ФСП, собственная валидация с фактическими результатами, документация и демонстрация |
| **P0 — обязательства проекта** | Две backend-категории; две сессии A/B; реальное изолированное исполнение кода; сохраняемая очередь проверок; вакансии и самостоятельные отклики |
| **P1 — существенно повышает оценку** | Расширение банка для независимых повторных циклов, сравнение нескольких методов оценки, дополнительные эксперименты с утечками, пользовательские проверки, доступный стенд |
| **P2 — полезные дополнения** | Регулярные короткие задания, мобильная адаптация |
| **P3 — при наличии времени** | Расширенная аналитика, ATS-концепция; AI-режим, embeddings, распознавание резюме и полноценный frontend assessment — после MVP, а не резерв шести дней |

Документ 02 описывает целевую систему. Отдельный AI-режим сохраняется в целевой модели и не реализуется в шестидневном MVP.

Вакансии и отклики опциональны по ТЗ, однако уже включены в релиз решением проекта. Их нельзя незаметно убрать под видом сокращения необязательных задач.

### Ограничения реализации

- Один modular monolith, одна PostgreSQL, API и worker из одного приложения.
- Отдельная Linux VM для runner; выполнение кода внутри API запрещено.
- Исполняемый язык первого релиза — JavaScript согласно архитектуре.
- Минимальный интерфейс: HTML, CSS и JavaScript с обращением к API, без отдельного frontend-фреймворка. Клиент и API размещаются под одним origin.
- Подготовка интерфейса начинается в день 1; день 5 — завершение и проверка сквозного взаимодействия.
- Профиль вводится вручную; распознавание резюме не требуется.
- ФСП — внутренний mock-адаптер с явно обозначенным происхождением данных.
- Runtime LLM, Redis, Celery и pgvector не нужны.
- Существующие документы уточняются по фактическому состоянию; переразбивка архитектуры на дополнительные файлы не становится отдельной задачей релиза.

### Банк заданий: граница демонстрационного объёма

Банк MVP: **6 backend-семейств (4 для A и 2 для B) + 1–2 frontend-семейства для демонстрации расширения, всего 7–8**. Для backend-семейств готовятся отдельные junior/middle-варианты и рубрики; смена уровня не делает знакомое семейство независимым. Сессии: 4 + 2 компактных кейса, до 30 + 15 минут; интервал 24–72 часа сохраняется. Меньшее число кейсов не гарантирует действующее покрытие критических навыков.

Это нижняя граница демонстрационного покрытия, а не доказательство устойчивости большого банка:

- Параметры одного шаблона не считаются независимыми семействами.
- Разные идентификаторы не делают похожие задания независимыми.
- Покрытие навыков проверяется по требованиям документа 02.
- Для каждого семейства нужны формулировка, допустимые параметры, рубрика, эталонные и ошибочные решения, проверка переноса.
- Для независимого второго цикла или перехода на другой уровень после знакомства со всеми семействами нужен дополнительный банк. До его появления подходящая попытка недоступна; повторные параметры не обходят правило независимости.
- При нехватке допустимых заданий система сообщает об этом; не ослабляет blueprint и не подтверждает грейд по неполному набору.

В релизе банк имеет статус **экспериментального**. Внутренняя проверка авторами продукта не выдаётся за независимое подтверждение сопоставимости сложности.

### Критический путь

1. Окружение и работающая изоляция.
2. Версии заданий, рубрики и допустимые варианты.
3. Сессии, проверка решений, достаточность доказательств.
4. Категория и безопасное представление кандидата.
5. Подборка, приглашение, согласие и доступ к контактам.
6. Сквозной интерфейс, проверка запуска, материалы сдачи.

Подбор можно разрабатывать на синтетических профилях параллельно assessment, но до завершения дня 4 необходимо проверить его с результатами настоящего движка.

### Общий Definition of Done

Функция готова, когда:

- Работает через согласованный API, а пользовательские действия доступны в интерфейсе.
- Состояние сохраняется и переживает перезапуск.
- Проверены основные разрешённые и запрещённые действия.
- Ошибки инфраструктуры отделены от результата кандидата.
- Документация соответствует фактическому поведению.
- Есть воспроизводимое доказательство: проверка, сценарий или сохранённый результат.

До сдачи обязательны: отсутствие известных утечек контактов, безопасное исполнение кода, прохождение основного сценария и запуск по инструкции.

## `docs/21_day_by_day_plan.md`

### День 1 — окружение и снятие основных технических рисков

**Backlog**

- Репозиторий, структура монолита, настройки окружения.
- Docker Compose, FastAPI, PostgreSQL, первая Alembic-миграция.
- Healthcheck и различение жизнеспособности API и готовности БД.
- Каркас worker и сохраняемой очереди.
- Подключение отдельной runner VM; пробное исполнение разрешённого JavaScript.
- Каркас веб-клиента: маршруты экранов, формы, работа с API.
- Базовые README, журнал решений и таблица требований.
- План 6 backend-семейств с рубриками junior/middle и 1–2 frontend-семейств расширения, распределение авторства.
- Разделение разработочных, контрольных и демонстрационных данных.

**Ответственные:** A — окружение и каркас клиента; B — runner и банк.

**Definition of Done**

- Другой участник поднимает приложение по инструкции.
- API отвечает, БД доступна, миграция применяется к пустой БД.
- Runner исполняет простой пример с ограничениями времени и ресурсов.
- Задача не получает сеть, секреты приложения и доступ к БД.
- Зафиксированы экраны, контракты и владельцы задач.
- Есть матрица покрытия навыков и назначенные авторы заданий.

**Контрольная точка:** отсутствие работающей изоляции — блокер. Нельзя компенсировать его запуском пользовательского кода внутри API.

### День 2 — пользователи, профили и подготовка assessment

**Backlog**

- Регистрация, вход, подтверждение email.
- JWT, refresh-сессии, выход, проверки ролей.
- Локальная почта через Mailpit; настройка SMTP для внешнего стенда при его наличии.
- Профили кандидата и работодателя.
- Контакты, согласия и настройки видимости.
- Базовое формирование PDF-профиля.
- Первые работающие экраны регистрации и профиля.
- Подготовка справочников, blueprint и задания для каждого типа проверки.
- Версионирование банка, сохранение seed и параметров варианта.
- Предварительная разметка данных для проверки подбора.

**Ответственные:** A — auth, профили и интерфейс; B — материалы и подготовка попыток.

**Definition of Done**

- Кандидат регистрируется, подтверждает email и сохраняет профиль через браузер.
- Email-токен одноразовый; неподтверждённый пользователь не начинает зачётную оценку.
- Пользователь не получает чужой профиль через подмену идентификатора.
- PDF формируется; контакты не появляются в представлениях без разрешения.
- У каждого используемого семейства есть версия, рубрика и проверочные примеры.
- Оба backend-грейда представлены вариантами и рубриками шести семейств; непроверенные материалы не включаются в зачёт.

### День 3 — опрос, тестирование и категоризация

**Backlog**

- Справочники специализаций, грейдов и технологий.
- Опрос и самостоятельный выбор предполагаемого грейда.
- Сборка варианта по blueprint.
- Сессии A/B, сроки доступа, сохранение ответов, завершение попытки.
- Worker, runner и обработка повторной доставки задания.
- Оценивание по рубрикам, проверка независимости и достаточности доказательств.
- Категория, история, сохранение прежнего подтверждения.
- Предложение теста ниже без автоматического понижения.
- Правила повторного прохождения и cooldown.
- Минимальная служебная обработка спорного результата.
- Начало реального по времени цикла для демонстрационной истории.

**Ответственные:** B — движок; A — интеграция профиля, правил доступа и экранов опроса, теста и результата. Проверка банка распределена между всеми.

**Definition of Done**

- Для Backend Junior и Backend Middle формируется корректный цикл A/B; frontend-пример не выдаёт подтверждённую категорию.
- Нельзя получить категорию только по самооценке, общей сумме или незавершённой B.
- Провал критического навыка не компенсируется другими результатами.
- Сбой runner не превращается в неправильный ответ.
- Повторная обработка не создаёт вторую оценку.
- Проверены границы временных ограничений с управляемым временем в тестах.
- В пользовательском сценарии интервал между сессиями не сокращён.
- Для демо сохранены прохождение A и время доступности B.

**Контрольная точка:** нехватка качественных заданий фиксируется как незакрытая часть релиза. Нельзя заменять её фиктивно подтверждёнными категориями.

### День 4 — обратный подбор и приглашения

**Backlog**

- EmployerNeed и его валидация.
- Hard filters, отдельная группа «требует уточнения».
- Детерминированный рейтинг по документу 03.
- Снимки подборок, уточнение потребности с сохранением предыдущего результата.
- Объяснения на основе фактических признаков.
- Приглашения с обязательной зарплатой «от–до».
- Статусы, срок действия, защита от повторной отправки.
- Принятие приглашения и выдача доступа к контактам в одной транзакции.
- Создание и публикация вакансии, самостоятельный отклик.
- Завершение демонстрационной сессии B после допустимого интервала.

**Ответственные:** B — подбор, интеграция подтверждённых навыков и проверки оценки; A — приглашения, вакансии и доступ.

**Definition of Done**

- Работодатель создаёт потребность и приглашает кандидата без опубликованной вакансии.
- Рейтинг воспроизводим при одинаковых данных и контрольном времени.
- Объяснение соответствует сохранённым признакам.
- Зарплата обязательна для приглашения и публикации вакансии.
- До согласия контакты скрыты; после принятия доступны только соответствующему работодателю.
- Самостоятельный отклик выдаёт доступ в пределах согласия кандидата.
- Проверены чужие идентификаторы, повторное принятие и конфликт принятия с отзывом/истечением.
- Цикл assessment связан с реальной подборкой.

### День 5 — сквозной интерфейс, ФСП и измерения

**Backlog**

- Завершение минимальных кабинетов кандидата и работодателя.
- Понятные состояния ожидания проверки, отсутствия кандидатов и ошибок.
- FSP mock: связь с профилем, достижения и маркировка источника.
- Seed-данные: кандидаты, потребности, вакансии, приглашения всех статусов.
- Проверки кейса без ФСП.
- Контрольный запуск matching и функциональных сценариев assessment.
- Метрики, примеры объяснений, таблица ограничений.
- Проверка PDF для разных прав доступа.
- Первая полная репетиция демонстрации.
- Создание release candidate.

**Ответственные:** A — интерфейс, privacy и сценарии; B — assessment, ФСП, данные и анализ ошибок.

**Definition of Done**

- Основной путь проходит через браузер без ручного редактирования БД.
- Кандидат без ФСП получает категорию и попадает в подборку.
- При отсутствии ФСП `F = 0`; остальные веса не пересчитываются.
- Демонстрационные достижения обозначены как mock.
- Получены фактические результаты проверок и сохранены исходные данные расчёта.
- Неизмеренные показатели помечены явно.
- Закрыты блокирующие дефекты основного сценария.
- Записан черновой резервный ролик.

**Ограничение:** с конца дня 5 новые функции не добавляются.

### День 6 — проверка сдачи и защита

**Backlog**

- Исправление блокирующих дефектов.
- Финальная проверка API, OpenAPI и соответствия документации.
- README: окружение, миграции, seed, почта, runner, запуск и устранение типовых проблем.
- Чистый запуск участником, который не готовил инструкцию.
- Экспорт документации в PDF или DOC.
- Презентация в PDF или PPTX.
- Отчёт валидации с фактическими результатами и ограничениями.
- Финальное видео, репетиция и проверка ссылок.
- Фиксация версии сдачи.

**Definition of Done**

- Основной сценарий и проверки приватности проходят на версии сдачи.
- Запуск проверен по инструкции в чистом окружении.
- Реальное исполнение кода проверено с runner; недоступность runner описана как ограничение, а не скрыта заглушкой.
- Репозиторий, документация, презентация и видео доступны.
- Числа на слайдах совпадают с отчётом.
- Демо укладывается в известный регламент; при отсутствии регламента используется восьмиминутная версия.
- Финальное видео соответствует сдаваемой версии.

### Правила валидации внутри графика

- Подготовка данных начинается в день 1, измерения — по мере готовности функций.
- Плановый синтетический набор из документа 04: 120 backend-кандидатов, 12 потребностей; разделение 40/80 кандидатов и 4/8 потребностей. Frontend — отдельные сценарии расширения без подтверждённого грейда.
- Эталон фиксируется до просмотра результата алгоритма. Проверяет его участник, не реализующий соответствующее правило, насколько позволяет команда.
- Для Recall@20 необходим полный эталон релевантности контрольного пула. При его отсутствии метрика остаётся неизмеренной.
- Два параметризованных варианта одного семейства не дают доказательства стабильности на независимых формах.
- Прохождения разработчиков используются для технической проверки, а не как независимый экспертный пилот.
- Без внешних участников и экспертов не заявляются точность определения реального грейда и достижение целевых порогов из документа 02.

## `docs/22_risks_and_mitigations.md`

| Риск | Ранний сигнал | Меры снижения | Действие при реализации |
|---|---|---|---|
| **Не успеть frontend** | К концу дня 2 нельзя зарегистрироваться и заполнить профиль через браузер | Начать каркас в день 1; простые формы, таблицы и карточки; минимум оформления | Убрать декоративные элементы и P2/P3; сохранить оба кабинета и основной путь |

| **LLM тормозит MVP** | Основной путь требует внешнего вызова модели | Подготовленный банк, детерминированная оценка и подбор | Удалить зависимость основного пути от LLM; offline-материалы проверять человеком |
| **Нет данных ФСП** | Невозможно проверить реестр или принадлежность достижения | Mock через интерфейс адаптера, явная маркировка, сценарий без ФСП | Продемонстрировать mock и ограничения; не заявлять реальную интеграцию |
| **Runner не готов или небезопасен** | Нет изоляции, лимитов или защищённого соединения в день 1 | Проверить инфраструктуру до разработки полного движка | Блокировать небезопасное выполнение; не переносить код кандидата в API |
| **Жюри не сможет запустить** | Инструкция требует знаний автора или личных секретов | Проверка чистого запуска, пример конфигурации, seed, отдельная инструкция runner | Доступный стенд и видео как дополнительные способы проверки; честно указать требования к локальному runner |
| **Слишком широкая архитектура** | Появляются дополнительные сервисы и платформенные компоненты | Один монолит, одна БД, очередь в PostgreSQL | Остановить инфраструктурные расширения, вернуться к критическому пути |
| **Утечка контактов** | Контакты присутствуют в общем DTO, PDF или старой подборке | Отдельное представление контактов, проверка текущего разрешения при каждом чтении | Блокер сдачи; исправить все затронутые способы доступа |
| **Некорректные статусы и гонки** | Двойное приглашение или доступ после проигранного принятия | Транзакции, идемпотентность, ограничения и проверки конкуренции | Исправить до записи финального демо |
| **Интервал A/B не помещается в демо** | Показ требует мгновенно завершить новый цикл | Заранее пройти полный цикл с настоящим интервалом | Показать новое прохождение и отдельно подготовленную историю; не менять часы продукта |
| **Метрики подогнаны под результат** | Веса меняются после просмотра контрольной выдачи | Фиксация версий и эталона до запуска | Старый контроль считать разработочным; не выдавать его за независимую проверку |
| **Нет измеримого улучшения** | Новый метод равен baseline или хуже | Сохранять результаты по всем потребностям, исследовать ошибки | Показать фактическое сравнение без обещания превосходства |
| **Срыв публичного показа** | Нестабильная сеть или внешний сервис | Подготовленные аккаунты, локальная почта, видео | Перейти к ролику и сохранённым артефактам |

### Порядок сокращения объёма

1. Не начинать P3.
2. Перенести P2.
3. Сократить P1, сохранив обязательный отчёт собственных проверок.
4. Упростить визуальное оформление и число дополнительных экранов.
5. Если P0 не помещается — явно согласовать изменение объёма или срока.

Нельзя сокращать приватность, обязательную зарплату, изоляцию кода, требования к доказательствам грейда или подменять измерения вымышленными результатами.

### Остаточные ограничения релиза

- Малый экспериментальный банк не гарантирует устойчивость к массовой утечке.
- Внешний помощник может сопровождать обе сессии.
- Синтетические данные не доказывают качество найма реальных людей.
- Нет подтверждённой производственной нагрузки и реального API ФСП.
- Шестидневный запуск не позволяет получить зрелую семидневную когорту приглашений для acceptance rate; демонстрационный переход статуса не заменяет такую метрику.

## `docs/23_demo_script.md`

### Цель показа

Продемонстрировать две связанные ценности:

1. Категория опирается на наблюдаемые результаты решения, переноса и подтверждения.
2. Работодатель получает объяснимую подборку и сам предлагает конкретному кандидату условия, включая зарплату.

Основной сценарий — **8 минут**, с возможностью сократить до 5 после уточнения регламента.

### Подготовка

- Два отдельных браузерных профиля: кандидат и работодатель.
- Новый email для регистрации и доступ к демонстрационному почтовому ящику.
- Подготовленный кандидат с завершённым циклом A/B и сохранёнными временными отметками.
- Кандидат без истории ФСП и кандидат с явно обозначенными mock-достижениями.
- Потребность, дающая непустую воспроизводимую подборку.
- Предложение с пересекающимся диапазоном зарплаты.
- Контрольная подборка top-10 для объяснения рейтинга.
- Отчёт измерений, презентация и резервный видеоролик.
- Чистое исходное состояние демо: приглашение ещё не принято.

Демонстрационные записи отделены от контрольных данных оценки качества.

### Сценарий

| Время | Действие | Что объяснить и доказать |
|---|---|---|
| **0:00–0:25** | Кратко представить продукт | Работодатель ищет по подтверждённым навыкам и первым предлагает условия |
| **0:25–1:05** | Зарегистрировать кандидата и подтвердить email | Реальное создание учётной записи и переход по письму |
| **1:05–1:35** | Заполнить основные поля, пройти опрос, выбрать грейд | Предполагаемый грейд выбирает кандидат; он ещё не подтверждён |
| **1:35–2:20** | Начать тест, показать решение и изменение условий | Проверяется перенос навыка, а не только знание опубликованного ответа |
| **2:20–2:55** | Перейти к заранее завершённому циклу A/B | Показать обе сессии, интервал, доказательства и полученную категорию |
| **2:55–3:35** | Работодатель создаёт потребность | Специализация, грейд, стек, формат, задачи и зарплатный диапазон |
| **3:35–4:20** | Открыть подборку и объяснение кандидата | Подтверждённые навыки, совпадение технологий, актуальность; условия допуска отделены от факторов рейтинга |
| **4:20–4:45** | Уточнить потребность | Новая подборка формируется с сохранением предыдущего результата |
| **4:45–5:20** | Выбрать кандидата и отправить приглашение | Вакансия не требуется; зарплата «от–до» обязательна; контакты ещё скрыты |
| **5:20–5:55** | Кандидат открывает и принимает приглашение | Видит компанию, предложение и зарплату до согласия |
| **5:55–6:15** | Обновить экран работодателя | Контакты доступны после принятия только нужному работодателю |
| **6:15–6:45** | Показать кандидата без ФСП | Он имеет категорию и участвует в подборе; бонус ФСП равен нулю |
| **6:45–8:00** | Открыть отчёт валидации | Фактические результаты, baseline, ошибки и ограничения |

При переключении между новым кандидатом и подготовленной историей прямо сказать:

> «Новый цикл требует второй сессии через 24–72 часа. Сейчас показываем заранее завершённое прохождение с сохранённой историей».

### Что показать в объяснении ранжирования

Использовать только подтверждаемые сведения из текущей карточки:

- «Подтверждён middle по экспериментальной методике».
- «Совпадают 4 из 5 требуемых технологий» — если это соответствует данным.
- «Есть подтверждённые результаты по ключевым навыкам».
- «Предпочтения по работе обновлены недавно».
- «Зарплатные ожидания пересекаются с предложением».

Если достижения взяты из mock-реестра, это должно быть видно на экране. Отсутствие ФСП не обозначается как отсутствие профессиональной квалификации.

### Блок метрик

На одном слайде представить:

| Направление | Что показывать |
|---|---|
| Подбор | Precision@10, Recall@20 при полном эталоне, nDCG@10; сравнение с baseline на одинаковых данных |
| Объяснения | Проверенные объяснения и найденные расхождения с фактическими признаками |
| Assessment | Результаты функциональных сценариев: критический навык, перенос, неполная B, недостаточные доказательства |
| Приватность | Проверки до/после принятия, чужих идентификаторов, PDF и самостоятельного отклика |
| Скорость | Время построения подборки с указанием объёма данных и окружения |
| Реальные грейды и стабильность | «Не измерено независимо», если внешнего пилота не было |

Синтетическую confusion matrix подписывать как проверку заданных сценариев. Не представлять её как точность определения грейда людей.

График совпадения технических повторов с одинаковыми входными данными доказывает воспроизводимость вычислений, а не устойчивость оценки человека.

### Дополнительный показ при наличии времени

- Неуспешный тест и добровольный выбор уровня ниже.
- Блокировка слишком ранней повторной попытки.
- Отсутствие подходящих кандидатов и группа уточнения.
- Публикация вакансии и самостоятельный отклик.
- Истечение или отзыв приглашения.
- Ошибка runner, которая не превращается в провал теста.

### Резервный сценарий

При проблеме стенда перейти к видео той же версии продукта. Затем показать сохранённые подборки, отчёт измерений и инструкцию запуска.

Видео подтверждает поведение прототипа, но не заменяет исходный код, документацию и честное описание условий воспроизведения.
