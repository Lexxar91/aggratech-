# 1. Цель продукта

Создать самостоятельную платформу подбора ИТ-специалистов, в которой работодатель инициирует контакт с кандидатом на основании проверенного профиля компетенций.

**Основная ценность:**

- Для работодателя — найти подходящих специалистов по подтверждённой специализации и грейду, получить объяснение подборки и предложить конкретные условия.
- Для кандидата — подтвердить квалификацию, использовать достижения ФСП как дополнительное доказательство навыков и получить предложение с зарплатой до начала общения.

Название «агрегатор вакансий» не должно смещать фокус: по §2 ТЗ парсинг сторонних сайтов и витрина вакансий не решают конкурсную задачу.

# 2. Целевые роли

| Роль | Основная задача |
| --- | --- |
| Кандидат | Подтвердить квалификацию, управлять профилем и отвечать на приглашения |
| Работодатель | Описать потребность, найти подходящих кандидатов и направить предложение |

Жюри — отдельная аудитория демонстрации и документации, но ТЗ не требует для него отдельного кабинета. Кабинеты администратора, модератора и представителя ФСП также не входят в обязательный MVP.

# 3. Ключевые пользовательские сценарии

**Основной сквозной сценарий:**

1. Кандидат регистрируется по электронной почте и подтверждает адрес.
2. Заполняет профиль, задаёт настройки видимости и предоставляет необходимые согласия.
3. Проходит опрос по отрасли и специализации, выбирает предполагаемый грейд.
4. Проходит тестирование; результат определяет подтверждённую категорию.
5. При наличии связывает профиль с ID участника ФСП.
6. Работодатель описывает потребность и получает категории и кандидатов с объяснением соответствия.
7. Уточняет подборку и выбирает конкретного кандидата.
8. Отправляет приглашение с предложением и диапазоном зарплаты.
9. Кандидат принимает или отклоняет приглашение; обе стороны видят статус.
10. После принятия работодатель получает доступ к контактам кандидата.

**Обязательные дополнительные ветки:**

- Кандидат без истории ФСП проходит основной путь без ошибки и искусственного требования иметь достижения.
- После неуспешного теста кандидат может выбрать тест на грейд ниже; автоматическое принудительное понижение запрещено.
- После уверенного прохождения кандидат может подтвердить более высокий грейд.
- Смена грейда ограничивается по времени; конкретный интервал выбирает команда.
- Кандидат видит историю опроса и тестирования.
- Работодатель ищет по банку кандидатов и уточняет запрос, сохраняя ранее полученную подборку.

**Необязательные сценарии:**

- Публикация вакансий и самостоятельный отклик кандидата.
- Регулярные короткие задания от работодателей.

# 4. Обязательные требования MVP

| Область | Минимальное требование |
| --- | --- |
| Учётные записи | Два ролевых кабинета; регистрация по email с подтверждением адреса |
| Профиль кандидата | Заполнение профиля и резюме; автоматическое формирование стандартизированного PDF-профиля |
| Ввод резюме | Допустима ручная форма: загрузка PDF с распознаванием является альтернативой |
| Первичная оценка | Опрос, выбор предполагаемого грейда, работающее тестирование, присвоение категории |
| Механика тестирования | Обоснованный подход к распространению заданий и сопоставимости сложности; единый неизменный тест недостаточен |
| Демонстрационные материалы | Несколько описаний вакансий и показ того, как на их основе формируются задания и тесты |
| Категория | Основа — специализация и подтверждённый грейд; основные направления для MVP определяет команда |
| Управление грейдом | История оценки, возможность тестирования на другой уровень, ограничение частоты смены |
| ФСП | Возможность связать профиль с ID; корректная работа без истории ФСП |
| Кабинет работодателя | Профиль компании и описание потребности в специалистах |
| Подбор | Категории по результатам оценки; ранжирование по подтверждённому профилю и соответствию потребности; краткое объяснение |
| Поиск | Фильтры по специализации, грейду, категории, стеку и подтверждённым достижениям ФСП |
| Контакт | Приглашение конкретному кандидату без обязательной опубликованной вакансии |
| Предложение | Описание, компания, способ связи и зарплата «от–до» в рублях |
| Взаимодействие | Принятие/отклонение приглашения; актуальные статусы для обеих сторон |
| Доступ | Кандидат видит только свои записи; контакты скрыты от работодателя до принятия приглашения или самостоятельного отклика |
| Приватность | Настройки видимости, согласие на обработку и публикацию данных |
| Валидация | Собственная процедура оценки качества, тестовые данные и полученные результаты |
| Проверяемость | Доступный исходный код без обфускации; воспроизводимые сборка и запуск |

Настройки приватности должны действовать во всех представлениях профиля, включая выдачу и формируемые документы.

Из нефункциональных требований зафиксировать защиту доступа, безопасное хранение паролей и токенов, работу в современных десктопных браузерах и доступность запуска на обычной машине или недорогом сервере. В ТЗ также заявлено соблюдение требований №152-ФЗ; этот этап фиксирует требование, но не оценивает юридическое соответствие.

# 5. Желательные, но не обязательные требования

- Публикация и редактирование вакансий работодателем; обработка откликов.
- Просмотр вакансий кандидатом, самостоятельный отклик и история его статусов.
- Регулярные короткие задания, поддерживающие актуальность профиля.
- Концепция защиты от фиктивных вакансий и недобросовестных работодателей.
- Концепция интеграции с ATS.
- Адаптивный интерфейс для телефонов и планшетов.
- Совместимость с будущим ФСП ID на базе Keycloak.
- Использование ML/NLP при наличии полезного, проверяемого результата.
- Контейнеризация и доступный развёрнутый прототип.
- Визуальное оформление с учётом брендбука ФСП.

Совместимость с Keycloak и выбор конкретного стека не являются обязательными. Реальные API и данные ФСП не предоставляются. Локальное подтверждение компании и модерация вакансий также не требуются для MVP.

Раздел §3.5 необходимо читать вместе с §3.2: технические ориентиры допускают обоснованное отступление. Это не отменяет явно обязательные функциональные требования, правила доступа и воспроизводимость запуска.

# 6. Требования к документации

По §3.4 итоговая документация должна описывать:

- Функциональную и компонентную архитектуру.
- Механику тестирования и устойчивость к распространению заданий.
- Подбор, ранжирование и категоризацию.
- Процедуру валидации и фактические результаты.
- Предполагаемую интеграцию с реестром ФСП.
- API; в §3.5 указан формат OpenAPI/Swagger с запросами, ответами и ошибками.
- Библиотеки и компоненты с версиями.
- Сборку, развёртывание и локальный запуск по шагам.

На текущем этапе эти пункты только фиксируются как обязательства будущей сдачи. Архитектура и API не проектируются.

Для финальной сдачи требуется ссылка на документацию в формате DOC или PDF. Два текущих Markdown-документа — рабочие артефакты анализа, а не замена всей документации к решению.

# 7. Требования к демонстрации и сдаче

**Промежуточная сдача:**

- Репозиторий с кодом.
- Краткое обоснование механик подбора и тестирования.
- Промежуточный прототип с базовым пользовательским сценарием.

**Финальная сдача:**

- Репозиторий с кодом.
- Презентация в PPTX или PDF.
- Документация в DOC или PDF.
- Желательно — доступный развёрнутый прототип.
- При отсутствии развёртывания — демонстрационное видео и понятная инструкция локального запуска.

На демонстрации обязательно показать путь от регистрации кандидата и тестирования до категории, поиска работодателем и приглашения конкретному человеку. Отдельно объяснить обе главные механики. Самостоятельный отклик показывать, если он реализован.

Для доказательства соблюдения требований дополнительно показать кандидата без истории ФСП, зарплату до начала общения и раскрытие контактов после согласия кандидата.

# 8. Ограничение по срокам: 6 дней

Срок 6 дней задан пользователем, а не PDF.

**Следствия для приоритетов:**

- Сначала закрыть работающий обязательный путь и два критерия с суммарным весом 60%.
- Использовать ограниченный, явно описанный набор специализаций и собственных тестовых данных.
- Заложить время на валидацию, документацию и демонстрацию внутри шести дней.
- Не делать завершение MVP зависимым от недоступного API ФСП.
- Добавлять необязательные функции после готовности основного сценария и доказательств его качества.

Вес критерия не отменяет обязательность требований, относящихся к другим критериям.

| Красивый интерфейс без работающей оценки | Категории остаются самоописанием; показывать связь результата теста с категорией |

# 10. Уточнения принятого релиза — 06.10.2026

Это решения команды по результатам ревью, а не дополнительные требования ТЗ. Источник согласованного объёма — [06_plan.md](06_plan.md).

- Подтверждаются Backend Junior/Middle в пределах Python, проверенных SQL/data- и HTTP/API-навыков. JavaScript и другие языки, а также производственный опыт автоматически не подтверждаются. Границы проверки видны в карточке и PDF.
- Две сессии A/B: до 30 и 15 минут. B открывается после окончательной сдачи A, без обязательного ожидания; возможен добровольный перерыв 5–10 минут. Ограничения повторов и смены опубликованного грейда сохраняются отдельно.
- Обязательный банк — 12 backend-семейств: формы X и Y, по 4 семейства A и 2 семейства B. У каждого семейства свои варианты junior/middle. Банк обеспечивает два полных цикла без повторения семейств для одного кандидата: первичную оценку и один переход на соседний уровень либо повтор того же уровня. После исчерпания нужен новый материал; это не неограниченный банк.
- Работающий переход на другой грейд, контрольное сравнение подбора и минимальная проверка качества оценки входят в P0. Демонстрационные frontend-задания перенесены после обязательного релиза; веб-интерфейс обеих ролей остаётся обязательным.
- Для нескольких описаний вакансий показывается цепочка «требование → навык → подготовленное семейство → тест → доказательство». Поддерживаемые запросы используют стандартный blueprint грейда: работодатель не меняет произвольно сложность или пороги.
- Вакансии и отклики остаются в согласованном релизе. Они не получают приоритет перед обязательными переходами грейда и валидацией двух основных механик.

Подробные правила и ограничения — в документах 02–06; численные показатели качества до экспериментов остаются целями, а не результатами.

## Уточнения релиза — 07.10.2026: Python и проверка на данных жюри

- Зачётные backend-задания выполняются на Python 3.14 вместо JavaScript/Node.js. Backend приложения уже на Python/FastAPI; веб-интерфейс сохраняет JavaScript. Подтверждаемые категории остаются Backend Junior/Middle, SQL/HTTP — в пределах фактически проверенных навыков. Второй язык и вторая специализация не добавляются.
- В обязательный объём проекта входит служебная загрузка заранее оценённых кандидатов и потребностей из JSON и запуск общего matching без регистрации, A/B, почты и runner. Контракт и инструкция — документ 03, §11; проверка — документ 04, §3.4.2.
- Это отдельная проверка подбора: импортированные категории обозначаются тестовыми данными и не подтверждаются нашим сервисом. Эталонные оценки пар хранятся отдельно и используются только для измерений после построения выдачи. При отсутствии полной разметки соответствующие метрики не измеряются.
- Поставляются схемы, пример, словарь полей и команды. Произвольные резюме без структурированных признаков и неподдерживаемые направления не маскируются под поддерживаемые данные. Это решение проекта для проверяемости, а не утверждение о заранее известном формате файлов жюри.
