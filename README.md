# Aggratech

Release candidate этапа 9: реализованы этапы 1–8 — профили, assessment A/B,
matching и автономный CLI, приглашения, вакансии и отклики, приватность и PDF.
Банк **`not_admitted`**: доступен явно обозначенный assessment demo, его категории
не являются подтверждённой квалификацией и не участвуют в подтверждённом подборе.
Независимое review и человеческий пилот пока не проведены; видео ещё нужно записать.
Это хакатонный прототип с **docker-limited runner**, не production-система.
Материалы и отдельный стенд RC: [docs/release/README.md](docs/release/README.md).

## Запуск жюри через Docker Compose

Нужны Docker Engine с Linux-контейнерами, cgroup v2 и включённым стандартным
seccomp, Docker Compose plugin, доступ к daemon и интернет для первоначальной
загрузки образов/зависимостей. VM, Python, PostgreSQL, uv и OpenSSL на хосте
устанавливать не нужно. На Docker Desktop Linux-контейнеры работают через его
собственную среду; отдельную runner VM проект не требует.

Образы Python 3.14.4, PostgreSQL 17, Mailpit и Docker CLI закреплены по digest,
зависимости — в `uv.lock`. Пароли Compose — локальные демонстрационные,
БД не публикуется на хост. Запускать из корня проекта:

```bash
test -f .env || cp .env.example .env
docker compose up --build -d
curl --fail http://127.0.0.1:18000/health/live
curl --fail http://127.0.0.1:18000/health/ready
docker compose exec worker python -m app.tools.runner_check
```

`runner_check` должен вернуть `status=completed`, `outputs=[42]` и фиксированный
runtime image. Compose сам применяет миграцию, загружает Python-образ и создаёт
mTLS-сертификаты в отдельных named volumes. Приватный ключ CA после генерации
удаляется. Только worker получает клиентский ключ, только контроллер — серверный.
Сертификаты демо действуют 7 дней. При их истечении перезапустить окружение:
`docker compose down`, затем `docker compose up -d`; генератор заменит bundles,
если до истечения осталось меньше суток. Это не production-управление PKI.

Клиент: http://127.0.0.1:18000, OpenAPI: http://127.0.0.1:18000/docs,
демонстрационная почта: http://127.0.0.1:18025.
`live` работает без БД; `ready` проверяет соединение и наличие миграции.
Миграция — отдельный одноразовый сервис, не действие каждого API-процесса.

## Кабинеты и письма (этап 2)

Откройте клиент по `http://127.0.0.1:18000/#register`, выберите роль и пароль
от 12 символов. Письмо появляется в Mailpit; откройте ссылку и нажмите
«Подтвердить email». Ссылка одноразовая (60 минут). Сброс пароля доступен
со страницы входа; ссылка действует 30 минут и отзывает все сессии аккаунта.

Кандидат вручную сохраняет профиль, контакты, зарплату в рублях/месяц gross,
предпочтения, заявленные технологии и согласие profile-v1. По умолчанию карточка
закрыта; включить видимость можно в настройках приватности. Работодателю
доступна только безопасная карточка, при согласии и отсутствии блокировки.
Закрытые контакты не включаются в неё или PDF работодателя. Собственный PDF
содержит контакты и кириллицу. Демо-оценка доступна в разделе проверки навыков;
зачётное присвоение категории требует независимого допуска банка.
Работодатель заполняет свой профиль компании. Все изменения хранятся в PostgreSQL.

Access JWT (15 минут) хранится только в памяти страницы. Refresh (7 дней) —
HttpOnly/Secure/SameSite=Strict cookie, с ротацией и серверным отзывом при replay.
Cookie-операции требуют разрешённый Origin и CSRF. Локальное демо открывать через
127.0.0.1 или localhost: браузер принимает Secure cookies для loopback.
Внешнее развёртывание требует HTTPS и явной настройки origins.
JWT-ключ создаётся автоматически в отдельном `app-secret` volume, API читает
его без права записи. Перезапуск сохраняет ключ, профили и сессии; удаление
volumes удаляет данные. Письма демонстрационные: Mailpit не доставляет их наружу.

## Автоматические проверки

```bash
docker compose --profile check build checks
docker compose --profile check run --rm checks
# Итоговая регрессия, включая настоящую изоляцию и браузер assessment:
docker compose --profile check run --rm checks sh -c 'alembic upgrade head && pytest -q -p no:cacheprovider'
```

Пакет использует отдельную PostgreSQL, проверяет auth, роли, владельцев, CSRF,
PDF с извлечением текста и браузерный сценарий в Chromium с настоящими письмами
Mailpit и перезапуском процесса API. Затем запускает Ruff lint/format и mypy.
Браузер находится только в образе проверок. SMTP-доставка допускает повтор письма
при аварии между отправкой и фиксацией; action token остаётся одноразовым.

## Проверки runner и полного банка

После запуска приложения:

```bash
docker compose --profile check build checks
docker compose --profile check run --rm checks pytest -q -m runner -p no:cacheprovider
docker compose exec runner-controller python -m runner.verify_isolation
docker compose exec worker python -m app.tools.bank_quality --output /tmp/bank-stage1
mkdir -p artifacts/bank-stage1
docker compose exec -T worker cat /tmp/bank-stage1/report.json > artifacts/bank-stage1/report.json
docker compose exec -T worker cat /tmp/bank-stage1/report.md > artifacts/bank-stage1/report.md
```

Общий пакет применяет миграции к отдельной настоящей PostgreSQL и запускает
проверки приложения, Ruff lint/format и строгий mypy. Отдельная команда с
`-m runner` проверяет реальные контейнеры задач. Проверяются
убийство и восстановление worker, конкурентный захват, повторы и атомарность
эффекта. `test-db` имеет временное хранилище; прикладная БД не очищается.
`verify_isolation` проверяет реальные Docker inspect: отсутствие socket у API
и worker, отдельную сеть контроллера, параметры живой задачи и её удаление.

`bank_quality` проверяет все 24 версии: 12 семейств Junior/Middle, в том числе
Python через тот же mTLS runner и структурированные SQL/data-ответы.
Код 0 и `technical_status=passed` означают только технический успех.
`admission_status=not_admitted` сохраняется до фактического независимого review.
Порядок review и текущие хеши: [комплект проверяющего](docs/release/human_checks.md).
При недоступности runner
отчёт имеет `incomplete`, код 1; заглушек и локального исполнения в API нет.
Повторный отчёт сохранять в новой папке — прежний не перезаписывается.

Пример очереди:

```bash
docker compose exec api python -m app.tools.queue_check --key stage1-demo
# После обработки worker повторить — тот же job_id, status=succeeded, effects=1.
docker compose exec api python -m app.tools.queue_check --key stage1-demo
```

При падении worker захваченное задание возвращается после lease; число попыток
ограничено, устаревший claim_token не создаёт повторный эффект. `docker compose
stop worker` позволяет вручную проверить ожидание; `docker compose start worker`
возобновляет обработку.

## Граница docker-limited и риски

Это **ограниченная контейнерная изоляция для демо, не эквивалент gVisor/VM и
не заявление о production-безопасности**. Задача и приложение используют одно
ядро Docker-хоста. Уязвимость ядра/runtime или компрометация контроллера могут
затронуть хост. Docker socket даёт контроллеру широкие права на daemon; внешняя
поверхность управления ограничена единственным mTLS-маршрутом `/execute`, который
принимает только исходник Python и JSON-входы. Произвольных Docker-команд,
пользовательских образов, mounts, runtime, privileged и изменения лимитов нет.

Контроллер не публикует порт на хост, работает в отдельной внутренней сети,
не получает БД, секретов приложения или исходников оценщика. API не подключён
к этой сети. Socket получает **только runner-controller**, никогда API, worker
или контейнер задачи. Контроллер — доверенный процесс с UID 0 для доступа к
socket; задача — UID/GID 65534. Одноразовый генератор PKI имеет только CHOWN и
DAC_OVERRIDE для подготовки volumes и не получает socket.

Контейнер задачи: network=none, read-only root, tmpfs 16 MiB с
noexec/nosuid/nodev, drop ALL capabilities, no-new-privileges, стандартный seccomp
Docker, privileged=false, 0.5 CPU, RAM 128 MiB без swap, 32 процесса.
Wall timeout — 5 секунд после старта attach; ввод — 128 KiB, исходник — 32 KiB,
совокупный stdout/stderr — 64 KiB. Пользователь не меняет политику.
Образ — чистый закреплённый CPython, без секретов, БД, томов хоста, банка и
исходников проверяющего кода. Только код и JSON-входы приходят через stdin.
Python `-I -B` сам по себе не является песочницей. Установка пакетов, реальные
HTTP-запросы и запуск произвольных веб-приложений не поддерживаются.

Задача удаляется после результата, ошибки, превышения вывода и тайм-аута.
При аварии самого контроллера принудительное удаление может задержаться до его
перезапуска: при старте он очищает оставшиеся контейнеры с собственным label.
Недоступность daemon или невозможность очистки — инфраструктурная ошибка,
не неверный ответ кандидата. Не открывать runner/daemon для публичных пользователей.

## Проверка другим участником

Другой участник использует отдельную копию проекта, включающую текущие
незакоммиченные файлы этапа, и новые named volumes, выполняет инструкцию запуска
и пакет проверок, сохраняет отчёт. Если проверяет на том же
Docker-хосте, сохраните прежний проект и задайте отдельные имя и порты:

```bash
export COMPOSE_PROJECT_NAME=aggratech-review
export APP_HTTP_PORT=18100
export MAILPIT_HTTP_PORT=18125
docker compose up --build -d
```

Named volumes и cleanup задач ограничены именем проекта; API и Mailpit доступны
на выбранных портах. Команды проверок выполняйте с теми же переменными.

Подтверждение для журнала: дата, участник, ОС/Docker/Compose, применённая к пустой
БД миграция `0002_auth_profiles`, результаты live/ready, `outputs=[42]`, pytest,
inspect и отчёта банка; замечания к инструкции. Секреты и ключи не передавать.

Review X1/X4: в `bank/private/stage1.json` сверить условия/рубрики и expected
для junior/middle, базовые и переносные случаи, обе корректные реализации и
типичные ошибки. Для X4 — остановку пагинации, пустую промежуточную страницу,
дедупликацию, перенос max_items/cursor_cycle и обнаружение трёх классов ошибок
подготовленными тестами. Записать результат и замечания; технический прогон
не заменяет review и не измеряет сложность для людей. Проверка объективности
и сложности по решению пользователя отнесена к финальному этапу 9.

## Материалы и обслуживание

`bank/blueprints.json` — матрица 12 семейств X/Y; `bank/private/stage1.json` —
первые X1/X4. `fixtures/demo` — три исходных описания вакансий,
`fixtures/validation` — паспорта, разделение данных и протокол добровольцев.
Материалы банка не раздаются через web-каталог. Seed не заменяет реальные
прохождения. Статус, стоимость, проверки и риски — в `docs/07_execution_plan.md`.

`docker compose down` сохраняет БД и сертификаты. `docker compose down -v`
удаляет данные текущего проекта и допустим только при намеренном сбросе.
При `ready=503` проверить `db` и `migrate` через `docker compose logs --tail=30`.
Занятые 18000/18025 заменить переменными APP_HTTP_PORT/MAILPIT_HTTP_PORT
и задать отдельный COMPOSE_PROJECT_NAME. Docker permission denied требует
настройки доступа к daemon по правилам машины. Для rootless Docker нестандартный
путь socket требует настройки и отдельной проверки; такой режим не заявлен
проверенным. Локальная разработка: Python 3.14.4, uv 0.12.23, `uv sync --locked`.

Основания: [Docker limits](https://docs.docker.com/engine/containers/resource_constraints/),
[SQLAlchemy locking](https://docs.sqlalchemy.org/en/20/core/selectable.html#sqlalchemy.sql.expression.Select.with_for_update),
[uv locked sync](https://docs.astral.sh/uv/concepts/projects/sync/).

## Assessment этапа 4: демонстрационный режим

После запуска Compose зарегистрируйте кандидата, подтвердите email через Mailpit
и откройте «Проверка навыков и история» в профиле. Примите правила и выберите
Junior/Middle. Сохранение черновика и окончательная фиксация — разные действия:
после фиксации базы открывается перенос, возврата к базе нет. Кнопка сдачи
фиксирует **сохранённые** черновики остальных заданий. После A можно сразу
начать B, не ожидая worker. Состояние оценивания обновляется отдельной кнопкой.
История и черновики восстанавливаются из БД после обновления и рестарта API.

Банк `bank/private/full.json` имеет технический отчёт
`bank/private/technical_report.json`, но `admission_status=not_admitted`.
До независимого review на этапе 9 доступен только demo. Успешное демо можно
добровольно опубликовать в собственном профиле/PDF; работодатель не получает
его как подтверждённую категорию. API `mode=credit` отклоняется проверкой
допуска, переменной отключения этой проверки нет. Смена материалов или оценщика
не должна молча переоценивать ранее начатый цикл: сохраняется снимок и хеш.

Апелляция доступна на странице цикла. Мотивированное служебное решение:

```bash
docker compose exec worker python -m app.tools.assessment_admin UUID uphold \
  --reviewer operator --reason 'Проверены ответы и журнал технического сбоя'
```

Другие действия: `review` — открыть проверку, `invalidate` — признать цикл
технически недействительным, `extend --seconds 300` — продлить текущий этап
или срок начала B, `retry` — повторить неготовую оценку тех же ответов.
Каждая операция требует причину и имя оператора, сохраняет аудит и историю
показанных семейств. Эти команды не меняют demo на credit и не выдают допуск банку.

Пакет этапа 4 (после сборки образа `checks`, миграции — до тестов):

```bash
docker compose --profile check run --rm checks sh -c \
  'alembic upgrade head && pytest -q tests/test_stage4_grading.py tests/test_stage4_cycles.py tests/test_stage4_browser.py tests/test_queue.py tests/test_auth_profiles.py tests/test_api.py -p no:cacheprovider'
```

Браузерный тест использует Chromium, Mailpit, PostgreSQL и настоящий runner:
создаёт новый demo-цикл через UI, фиксирует A/B, перезапускает API, публикует
результат и читает PDF. Это автоматизированный сценарий с подготовленными
ответами, **не человеческая валидация** объективности или сложности банка.


## Matching и ФСП mock (этап 5)

После подтверждения email работодатель открывает «Потребности и подбор».
Три шаблона заполняют описания и приоритеты; бюджет и требования задаются
вручную. Любое поле редактируется. Сохранение создаёт новую версию,
«Создать подборку» — снимок этой версии. Основная группа и «Требуется
уточнение» разделены; Junior и Middle не смешиваются. Сохранение и скрытие
карточки действуют внутри потребности. Для сравнения выберите две карточки
одной категории и группы; перед открытием интерфейс перечитывает подборку.
Старые снимки повторно проверяют приватность, блокировки, публикацию и
допуск исходного доказательства; недоступная карточка становится заглушкой.
Контакты не раскрываются. Методика экспериментальная, область Python/SQL/HTTP.

Банк пока `not_admitted`: демонстрационные прохождения в подтверждённый подбор
не входят. Полная приёмка подбора на реальных зачётных результатах требует
review на этапе 9. Fixture для CLI живут только в памяти и не импортируются
в продуктовую БД.

Автономный запуск на новом JSON-наборе без аккаунта и инфраструктуры:

```bash
python -m app.tools.matching_check --write-example /tmp/matching-example
python -m app.tools.matching_check --input /tmp/matching-example/dataset.json --validate-only
python -m app.tools.matching_check --input /tmp/matching-example/dataset.json --labels /tmp/matching-example/labels.json --output /tmp/matching-results
```

В репозитории поставляется `fixtures/jury/matching/`: схемы, словарь,
синтетические dataset/labels и инструкция преобразования собственного набора.
Labels загружаются только после вычисления всех B0/B1/B2. Неполнота разметки
делает основные метрики всей потребности `not_measured`; отсутствующая пара
не означает отрицательный пример. Пул oracle берётся из labels независимо
от фильтров алгоритма. `Precision@10` всегда делится на 10; `Recall@20` и
идеальный nDCG используют полный oracle-пул своего грейда и группы.

Запуск образа полностью без сети (вход read-only, отдельный выход; БД и
секреты не подключаются):

```bash
mkdir -p artifacts/matching-output
docker run --rm --user "$(id -u):$(id -g)" --network none --read-only --tmpfs /tmp \
  --cap-drop ALL --security-opt no-new-privileges:true \
  -v "$PWD/fixtures/jury/matching:/input:ro" \
  -v "$PWD/artifacts/matching-output:/output" \
  aggratech-stage1:app python -m app.tools.matching_check \
  --input /input/dataset.json --labels /input/labels.json --output /output/result
```

Контейнер CLI работает с UID текущего пользователя и пишет в его отдельную
выходную папку. Успех создаёт целиком
четыре файла: `rankings.json`, `metrics.json`, `report.md`, `run_manifest.json`.
Непустой выход не перезаписывается. Manifest фиксирует исходные хеши dataset
и labels раздельно, версии схем/формулы/справочника/адаптера, хеши кода,
`as_of`, количество записей и фактическую длительность.
Коды выхода: 0 — успех (также без labels); 2 — ввод/аргументы; 1 — техническая
ошибка. `errors.json` содержит путь поля и код без исходного профиля.
Лимиты: 10 MiB на файл, 1000 кандидатов, 100 потребностей, 100000 пар.
Неизвестные поля/коды, повторные ключи/ID/пары, ошибочные ссылки, bool вместо
чисел, несопоставимые методики и будущие подтверждения отвергаются.
Порядок B2: Score → T → K → candidate_id внутри категории и группы.

ФСП работает только через mock, не настоящий реестр. На экране «ФСП mock»
кандидат с подтверждённым `fsp-demo-anna@example.com` может привязать
`demo-anna` кодом `demo-anna-proof`, затем синхронизировать историю.
Для пустой истории: `fsp-demo-empty@example.com` / `demo-empty` /
`demo-empty-proof`; для временной ошибки: `fsp-demo-unavailable@example.com`
/ `demo-unavailable` / `demo-unavailable-proof`.
Это публичные синтетические идентификаторы и demo-коды, не секреты.
Чужой email или один ID без правильного кода не подтверждают принадлежность.
Повторная синхронизация не дублирует события; отзыв удаляет связь и кэш.
Записи имеют `source=fsp_mock`, не подтверждают реальные достижения и дают
`F=0` в продукте. Внешний тестовый dataset может явно задавать `fsp_verified`
для проверки формулы; это не верификация людей.

### Приглашения и контактное согласие (этап 6)

Работодатель открывает потребность → подборку → «Пригласить», указывает
предложение, обе положительные границы зарплаты в RUB/месяц gross, формат,
существенные условия и контакт представителя. Вакансия не требуется.
Отправленное предложение неизменно; изменения потребности его не переписывают.
Для исправления нужно отозвать приглашение и отправить новое. Срок — семь суток;
одно активное или принятое приглашение на пару «потребность — кандидат».
Повтор отправки с тем же ключом возвращает прежнее приглашение, другой payload
с этим ключом отклоняется. Новое действие при действующем приглашении — 409.

В кабинете кандидата «Приглашения» позволяет открыть, принять или отклонить
предложение. При принятии кандидат выбирает email, телефон и/или мессенджеры
и явно подтверждает `contacts-v1`. До этого контакты закрыты. Разрешение
получает только отправитель; безопасная карточка остаётся отдельным DTO,
контакты читаются отдельным запросом и включаются в PDF только по разрешению.
«Закрыть контакты этой компании» отзывает все её разрешения, сохраняя
исторический статус `accepted`. Блокировка компании также закрывает разрешения
и отзывает незавершённые приглашения. Отзыв общего согласия закрывает все
контактные разрешения; новое согласие или снятие блока не оживляет старые.
Скрытие из поиска запрещает новые приглашения, но позволяет ответить на уже
полученное предложение незаблокированной компании.

Письма через Mailpit содержат статус и ссылку, без копии контактов кандидата.
При каждом открытии API/PDF проверяются текущие права. Уже скачанный PDF
или ранее увиденные данные невозможно отозвать удалённо.
Банк пока `not_admitted`: демо-категории не попадают в подборку и не открывают
отправку приглашений. Проверки со синтетическими квалификациями выполняются
только в отдельной `aggratech_test` и не подтверждают квалификацию людей.

## Вакансии и самостоятельные отклики

Работодатель открывает «Вакансии», создаёт вакансию с обязательным диапазоном
зарплаты в рублях до налогов и условиями работы. Опубликованную вакансию можно
редактировать или закрыть. Закрытие прекращает новые отклики, сохраняя историю.
При параллельном редактировании устаревшая версия отклоняется.

Подтвердив email, кандидат выбирает вакансию, отмечает разрешённые контакты
и явно соглашается на их передачу этому работодателю. Отклик и разрешение
сохраняются одной транзакцией; условия вакансии копируются в неизменяемый
снимок. Повторная подача возвращает прежний отклик и не меняет согласие.
Работодатель может отметить просмотр, принять или отклонить отклик; кандидат
может отозвать его, включая ранее принятый или отклонённый.

Отзыв отклика закрывает только его разрешение. Другой действующий отклик
или принятое приглашение продолжает разрешать собственный набор контактов;
отказ работодателя и закрытие вакансии сами по себе согласие не отзывают.
Общий отзыв согласия и блокировка работодателя закрывают все соответствующие
разрешения. Карточки, контакты и новые PDF проверяют текущую приватность.
Отклик не требует подтверждённой категории: ручной профиль показывается без
подтверждённой квалификации, а gate банка `not_admitted` сохраняется.

## Assessment и автономный matching

Опрос и выбор Junior/Middle открывают цикл с четырьмя заданиями A (30 минут)
и двумя B (15 минут). B начинается после сдачи A, не позднее 24 часов;
черновики, фиксация, история, апелляции и выбор публикации сохраняются.
Demo явно маркируется; до допуска банка зачётный режим закрыт. Повтор одного
грейда — не ранее семи суток, не более двух завершённых циклов за 30 суток;
банк учитывает показанные семейства и может исчерпаться.

Работодатель задаёт потребность из одного из трёх редактируемых шаблонов.
Matching учитывает фильтры, отдельно показывает неизвестные условия, сохраняет
версии выдачи, объяснения и текущую приватность. При `not_admitted` ожидается
пустая подтверждённая выдача. ФСП подключается только как явно обозначенный mock.
Без подтверждённого ФСП `F = 0`, остальные веса не перераспределяются.

Автономный `app.tools.matching_check` работает по JSON без БД, почты и runner;
labels применяются только после ранжирования. Инструкция из трёх команд,
схемы, тестовые данные и четыре артефакта: [RC и CLI](docs/release/README.md).
Синтетические баллы и метрики не подтверждают квалификацию или качество найма.
